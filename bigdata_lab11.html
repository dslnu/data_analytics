Big Data Analytics: Lab 11

Table formats: Delta Lake, Apache Iceberg, Spark

In the lecture we saw that a table format adds three things on top of Parquet files: which files belong to the table now, atomic changes, and a history of versions. In this lab you build such tables yourself and look inside them:

  1. Delta Lake with deltalake (delta-rs, written in Rust: no JVM)
  2. Apache Iceberg with pyiceberg and a catalog in a local SQLite file
  3. DuckDB as a second engine reading both tables
  4. Spark as a third engine: SQL, Merge-on-Read deletes, maintenance procedures

Everything runs locally, without Docker and without cloud accounts. Parts 1–3 need only pip. Part 4 needs Java, which we also install with pip.

Important

Keep a short report as you go: the answers to the questions marked Q, with the output that supports them.

Setup

Use a separate environment with Python 3.12: PySpark 3.5 does not support newer Pythons.

uv venv -p 3.12 .venv-lake
source .venv-lake/bin/activate          # Windows: .venv-lake\Scripts\activate

# Parts 1-3
uv pip install duckdb deltalake "pyiceberg[sql-sqlite,pyarrow,pyiceberg-core]" pandas jupyter

# Part 4
uv pip install "pyspark==3.5.*" "delta-spark==3.3.*" "jdk4py>=21,<22"

(Without uv: python3.12 -m venv .venv-lake and pip install ... work the same.)

NoteWhy jdk4py?

Spark runs on the JVM and needs Java 17 or 21. Newer Java versions do not work with Spark 3.5. jdk4py is a pip package that ships a Java 21 runtime, so you do not need to install Java system-wide. If you already have JDK 17 or 21, you can skip it.

Windows: Spark needs extra Hadoop binaries (winutils.exe) to write local files. Do Part 4 in WSL2, where these instructions work unchanged.

Work in a Jupyter notebook. All tables go into one working directory:

import os, json, glob, shutil
import duckdb

W = os.path.abspath("lakehouse_lab")
shutil.rmtree(W, ignore_errors=True)
os.makedirs(W)

con = duckdb.connect()

Data

The synthetic taxi trips from the lectures: 300,000 trips, one per minute, over about 7 months.

con.sql("""
SELECT setseed(0.42);
CREATE TABLE trips AS
SELECT i                                                   AS trip_id,
       TIMESTAMP '2025-01-01' + to_seconds(i * 60)         AS pickup_ts,
       ['cash', 'card', 'app'][1 + (hash(i) % 3)::INTEGER] AS payment,
       1000 + (random() * 50)::INTEGER                     AS zone_id,
       round(random() * 100, 2)                            AS fare
FROM range(300000) t(i);
""")
trips = con.sql("FROM trips ORDER BY trip_id").to_arrow_table()
trips.schema

Part 1: Delta Lake with delta-rs

1.1 Many small writes

Write the trips in 10 batches, as a streaming job would:

from deltalake import DeltaTable, write_deltalake

delta_path = f"{W}/delta_trips"
batch = 30_000
for k in range(10):
    write_deltalake(delta_path, trips.slice(k * batch, batch), mode="append")

dt = DeltaTable(delta_path)
print("version:", dt.version(), " files:", len(dt.file_uris()))

1.2 Read the log

def show_log(path):
    for f in sorted(glob.glob(f"{path}/_delta_log/*.json")):
        actions = [next(iter(json.loads(line))) for line in open(f)]
        print(os.path.basename(f), actions)

show_log(delta_path)

Open _delta_log/00000000000000000000.json in an editor.

  • Q1. What do the protocol and metaData actions contain? Where is the schema?
  • Q2. Each add action has a stats field. What is in it? Which lecture concept is this, and how could an engine use it for WHERE trip_id < 1000?

1.3 Compaction

dt = DeltaTable(delta_path)
print("files before:", len(dt.file_uris()))
print(dt.optimize.compact())
dt = DeltaTable(delta_path)
print("files after:", len(dt.file_uris()), " version:", dt.version())

Look at the new commit with show_log(delta_path). Try also dt.optimize.z_order(["zone_id", "pickup_ts"]) and check its commit.

  • Q3. Compaction created a new version. Did it change the data? What did it change, and why does it make queries faster? (Recall the small-files problem.)

1.4 Update and delete

dt = DeltaTable(delta_path)
dt.update(predicate="payment = 'cash'", updates={"fare": "fare * 1.1"})

show_log(delta_path)

Part 2: Apache Iceberg with PyIceberg

2.1 Catalog and a partitioned table

The catalog is a SQLite file. It plays the role that Hive Metastore, Glue, or a REST catalog play in production.

from pyiceberg.catalog.sql import SqlCatalog
from pyiceberg.transforms import MonthTransform

catalog = SqlCatalog("lab", uri=f"sqlite:///{W}/catalog.db", warehouse=f"file://{W}/warehouse")
catalog.create_namespace("taxi")

tbl = catalog.create_table("taxi.trips", schema=trips.schema)
with tbl.update_spec() as spec:
    spec.add_field("pickup_ts", MonthTransform(), "pickup_month")   # hidden partitioning

tbl.append(trips)
print(tbl.spec())
tbl.inspect.partitions().select(["partition", "record_count", "file_count"]).to_pandas()

2.2 The metadata tree

for f in sorted(glob.glob(f"{W}/warehouse/taxi/trips/**/*", recursive=True)):

2.5 Optimistic concurrency

Two writers load the same table version and both append:

a = catalog.load_table("taxi.trips")
b = catalog.load_table("taxi.trips")
a.append(trips.slice(0, 10))
b.append(trips.slice(10, 10))      # b's view is now stale
print(len(catalog.load_table("taxi.trips").snapshots()), "snapshots")
  • Q12. Read the log message printed by the second append. What happened, step by step? Why is a retry safe for two appends? Give an example of two concurrent operations where a blind retry would be wrong.

Part 4: Spark

4.1 Session

import os, jdk4py
os.environ["JAVA_HOME"] = str(jdk4py.JAVA_HOME)     # skip if you use your own JDK 17/21

from pyspark.sql import SparkSession

spark = (SparkSession.builder
    .appName("lakehouse-lab")
    .master("local[2]")
    .config("spark.sql.session.timeZone", "UTC")
    .config("spark.jars.packages",
            "io.delta:delta-spark_2.12:3.3.2,"
            "org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.10.0")
    .config("spark.sql.extensions",
            "io.delta.sql.DeltaSparkSessionExtension,"
            "org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions")
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .config("spark.sql.catalog.ice", "org.apache.iceberg.spark.SparkCatalog")
    .config("spark.sql.catalog.ice.type", "hadoop")
    .config("spark.sql.catalog.ice.warehouse", f"{W}/spark_warehouse")
    .getOrCreate())
spark.sparkContext.setLogLevel("ERROR")
spark.version

The first start downloads the Delta and Iceberg jars (~40 MB) from Maven Central, so it needs internet and takes a minute. They are cached in ~/.ivy2.

4.3 Iceberg with Merge-on-Read

spark.sql("""
CREATE TABLE ice.taxi.trips (trip_id BIGINT, pickup_ts TIMESTAMP, payment STRING, zone_id INT, fare DOUBLE)
USING iceberg
PARTITIONED BY (months(pickup_ts))
TBLPROPERTIES ('write.delete.mode' = 'merge-on-read')
""")

con.sql(f"COPY trips TO '{W}/trips.parquet' (FORMAT parquet)")
spark.sql(f"""
INSERT INTO ice.taxi.trips
SELECT trip_id, CAST(pickup_ts AS TIMESTAMP), payment, zone_id, fare
FROM parquet.`{W}/trips.parquet`
""")
spark.sql("DELETE FROM ice.taxi.trips WHERE zone_id = 1000")

spark.sql("SELECT snapshot_id, operation FROM ice.taxi.trips.snapshots").show(truncate=False)
spark.sql("SELECT content, record_count, file_path FROM ice.taxi.trips.files").show(truncate=60)

content is 0 for data files and 1 for positional delete files.

  • Q18. Compare with Q14. What did Spark write for the DELETE? What does a reader now have to do? When is Merge-on-Read the better choice?

4.5 Maintenance

from datetime import datetime, timezone
now = datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M:%S")

spark.sql("""CALL ice.system.rewrite_data_files(table => 'taxi.trips',
             options => map('delete-file-threshold', '1'))""").show()
spark.sql(f"""CALL ice.system.expire_snapshots(table => 'taxi.trips',
              older_than => TIMESTAMP '{now}', retain_last => 1)""").show()
spark.sql("SELECT content, record_count FROM ice.taxi.trips.files").show()

Part 5 (optional): the platform view

minilake emulates the Databricks API locally (pip install minilake, then minilake --port 8000), with Unity Catalog-style catalog.schema.table names and a web SQL editor at /ui. It runs SQL on DuckDB and stores Delta tables on disk. It is a young project: treat it as a way to see what working on Databricks feels like, not as a reference implementation.
