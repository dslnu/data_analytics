Big Data Analytics: Lab 2

Cython

First, install Cython and Numba:

uv add cython
uv add numba

Then we can load Cython extension in Jupyter:

%load_ext Cython

Define a function that generates a list of first \(n\) primes:

ImportantPure Python 
def primes1(nb_primes):
    p = [0] * 1000
    if nb_primes > 1000:
        nb_primes = 1000

    len_p = 0  # The current number of elements in p.
    n = 2
    while len_p < nb_primes:
        # Is n prime?
        for i in p[:len_p]:
            if n % i == 0:
                break

        # If no break occurred in the loop, we have a prime.
        else:
            p[len_p] = n
            len_p += 1
        n += 1

    # Let's copy the result into a Python list:
    result_as_list = [prime for prime in p[:len_p]]
    return result_as_list
ImportantPure Python results

We can measure its execution time:

%timeit primes1(100)
154 μs ± 953 ns per loop (mean ± std. dev. of 7 runs, 10,000 loops each)

Using Cython in Pandas

Define a random DataFrame:

import pandas as pd
import numpy as np

df = pd.DataFrame(
    {
        "a": np.random.randn(1000),
        "b": np.random.randn(1000),
        "N": np.random.randint(100, 1000, (1000)),
        "x": "x",
    }
)

Define functions that will be applied to the DataFrame:

ImportantPure Python 
def f(x):
    return x * (x - 1)


def integrate_f(a, b, N):
    s = 0
    dx = (b - a) / N
    for i in range(N):
        s += f(a + i * dx)
    return s * dx

Apply functions to DataFrame:

%timeit df.apply(lambda x: integrate_f(x["a"], x["b"], x["N"]), axis=1)
28.7 ms ± 66.3 μs per loop (mean ± std. dev. of 7 runs, 10 loops each)

Now let’s use Cython-annotated functions:

def f_typed2(x: cython.double) -> cython.double:

Numba

Either add engine="numba" parameter to Pandas functions, or add a @jit annotation to Python funcs.

WarningNumba-annotated code 
import numba


@numba.jit
def f_numba(x):
    return x * (x - 1)


@numba.jit
def integrate_f_numba(a, b, N):
    s = 0
    dx = (b - a) / N
    for i in range(N):
        s += f_numba(a + i * dx)
    return s * dx


@numba.jit
def apply_integrate_f_numba(col_a, col_b, col_N):
    n = len(col_N)
    result = np.empty(n, dtype="float64")
    assert len(col_a) == len(col_b) == n
    for i in range(n):
        result[i] = integrate_f_numba(col_a[i], col_b[i], col_N[i])
    return result


def compute_numba(df):
    result = apply_integrate_f_numba(
        df["a"].to_numpy(), df["b"].to_numpy(), df["N"].to_numpy()
    )
    return pd.Series(result, index=df.index, name="result")
WarningNumba Results

PyO3 (Rust)

Cython is a dialect – Python plus C type declarations, compiled through C. PyO3 takes a different route: write the extension in Rust, a real systems language, and expose functions to Python. You get memory safety, cargo’s package ecosystem, and modern tooling – at the cost of learning Rust and a heavier build step. It has become the default way to write Rust extensions for Python (used by pydantic-core, polars, cryptography, ruff, …).

Prerequisites: a Rust toolchain (rustup / cargo) and the maturin build tool:

uv add --dev maturin

The crate lives in _files/integ_rs/ and has three files:

_files/integ_rs/Cargo.toml

[lib]

[dependencies]

[profile.release]

_files/integ_rs/pyproject.toml – tells maturin how to build:

[build-system]

build-backend = "maturin"

[project]
name = "integ_rs"
version = "0.1.0"
requires-python = ">=3.14"

[tool.maturin]
bindings = "pyo3"

_files/integ_rs/src/lib.rs – the same integrate_f as before, in Rust:

use pyo3::prelude::*;

#[inline]
fn f(x: f64) -> f64 {
    x * (x - 1.0)
}

/// Numeric integration of f from a to b using n rectangles.
#[pyfunction]
fn integrate_f(a: f64, b: f64, n: i64) -> f64 {
    let dx = (b - a) / n as f64;
    let mut s = 0.0;
    for i in 0..n {
        s += f(a + i as f64 * dx);
    }
    s * dx
}

/// Apply integrate_f over whole columns in one call.
#[pyfunction]
fn apply_integrate_f(a: Vec<f64>, b: Vec<f64>, n: Vec<i64>) -> Vec<f64> {
    a.iter()
        .zip(b.iter())
        .zip(n.iter())
        .map(|((&ai, &bi), &ni)| integrate_f(ai, bi, ni))
        .collect()
}

#[pymodule]
fn integ_rs(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(integrate_f, m)?)?;
    m.add_function(wrap_pyfunction!(apply_integrate_f, m)?)?;
    Ok(())
}

%memit – peak memory of an expression

uv add memory_profiler
import sys
%load_ext memory_profiler
%memit big_list = [0] * 10_000_000
print("list overhead :", sys.getsizeof(big_list) / 1e6, "MB of pointers")
print("ndarray nbytes:", np.zeros(10_000_000, dtype="int64").nbytes / 1e6, "MB, contiguous")
peak memory: 361.58 MiB, increment: 76.75 MiB
list overhead : 80.000056 MB of pointers
ndarray nbytes: 80.0 MB, contiguous

%memit reports the peak memory of the expression: ~76 MiB just to hold 10 million pointers to the same cached 0. The equivalent int64 array is 80 MB in one contiguous block – same element count, but the cache can stream it.

scalene – CPU + GPU + memory, and where the time goes

uv add scalene

scalene is a sampling profiler with low overhead (~10–20%). Its report is a browser UI, or a terminal table with --cli, so it does not render usefully inside a notebook – run it on a script:

scalene --cli --reduced-profile myscript.py     # terminal, significant lines only
scalene myscript.py                             # interactive HTML report

What makes it worth learning for this lab: for every line it splits the time into

  • Python time – interpreter overhead; the part Cython / Numba / PyO3 can remove
  • native time – already inside compiled C (NumPy, BLAS, …); rewriting this line will not help
  • system time – I/O and waiting

and alongside CPU it tracks memory over time and copy volume (MB/s copied), which catches accidental copies – np.array(some_list) in a loop, a pandas .copy() you did not mean, df[mask] in a hot path.

TipReading it
  • a line that is ~95% native time is not your problem – it is already fast C
  • a line that is ~90% Python time inside a loop is exactly what you port to Cython / Numba / Rust
  • a line with high copy volume is an allocation to hoist out of the loop
NoteOther tools
  • %mprun – line-by-line memory (needs the function in an importable file)
  • py-spy – sampling profiler that attaches to an already-running process, no code changes: py-spy top --pid <PID>, py-spy dump --pid <PID>
  • snakeviz – browser icicle/flame view of a saved run: python -m cProfile -o out.prof script.py && snakeviz out.prof
  • viztracer – full execution timeline, viewable in Perfetto / chrome://tracing

Project ideas

Data-science flavoured. Pick one. In each case: start from the natural slow version (a df.apply(..., axis=1), a groupby().apply(), a rolling().apply(), or a plain Python loop), then produce at least three faster variants (NumPy-vectorised, Numba, Cython, PyO3), profile with line_profiler / scalene at each step to confirm where the time goes, and finish with a speedup table plus a paragraph on which approach was the least effort for the most gain. Reuse _files/transactions.csv and _files/depression_data.csv from Lab 1 where possible.

  1. Row-wise feature engineering / business rules. Build a customer “risk score” or segment label from 10+ nested if/else rules with lookups and date arithmetic over transactions.csv. Baseline: df.apply(fn, axis=1). Variants: vectorised np.select / np.where; a Numba kernel over the raw column arrays; a PyO3 function taking the columns. The single most common real-world “my pandas is slow” case.
  2. Custom group-by aggregation pandas cannot vectorise. Per-customer metrics over transactions.csv: time since previous purchase, longest fraud-free streak, a recency-weighted spend score. Baseline: groupby("customer_id").apply(py_fn). Variants: sort once, then a Numba pass over the sorted arrays; a Rust equivalent; whatever pure-pandas trick you can find.
  3. Rolling-window features with a custom reducer. On a synthetic price / sensor series: rolling regression slope, rolling entropy, rolling max-drawdown. Baseline: series.rolling(w).apply(fn, raw=True). Variants: an explicit Numba sliding window, Cython, PyO3; compare against bottleneck / numbagg.
  4. Pairwise similarity / nearest-neighbour from scratch. Cosine or Euclidean similarity across N rows for deduplication, a simple recommender, or k-NN (and, as a stretch, k-means – the assignment step is the same loop). Pure Python -> NumPy broadcasting (watch the memory blow-up – read scalene’s copy volume) -> blocked Numba -> PyO3. Benchmark against scipy.spatial.distance.cdist and sklearn.
  5. Geospatial: nearest facility + radius counts. Millions of synthetic (lat, lon) points and a few hundred reference locations: for each point find the nearest reference by haversine distance, and count points within R km of each reference. Vectorised NumPy -> Numba -> PyO3. Report points/second.
  6. Text analytics from scratch: n-gram / co-occurrence counts. Tokenise a text column and build n-gram frequencies or a word co-occurrence matrix. Pure-Python dict counting -> arrays + hashing -> Cython -> Rust (very strong here). Benchmark against sklearn.feature_extraction.text.CountVectorizer.
  7. Bootstrap / permutation testing. B = 100_000 resamples of depression_data.csv, computing a statistic each time – a bootstrap CI for mean income by education level, or a permutation test for a group difference. The resample-and-reduce loop is embarrassingly parallel: pure Python -> NumPy -> Numba parallel=True -> PyO3 with rayon. Report resamples/second and the effective parallel speedup.
