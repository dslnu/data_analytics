Data representations

Programs usually work with data in (at least) two different representations:

  • In memory, data is kept in objects, structs, lists, arrays, hash tables, trees, and so on. These data structures are optimized for efficient access and manipulation by the CPU (typically using pointers).
  • When you want to write data to a file or send it over the network, you have to encode it as some kind of self-contained sequence of bytes (for example, a JSON document).

Binary JSON: MessagePack

  • The first byte, 0x83, indicates that what follows is an object (top four bits = 0x80) with three fields (bottom four bits = 0x03)
  • The second byte, 0xa8, indicates that what follows is a string (top four bits = 0xa0) that is eight bytes long (bottom four bits = 0x08)
  • The next eight bytes are the field name userName in ASCII indicated previously, there’s no need for any marker to tell us where the string ends (or any escaping)
  • The next seven bytes encode the six-letter string value Martin with a prefix 0xa6

Dremel

Column storage is easiest to understand in a relational data model, but it applies equally to nonrelational data.

For example, Parquet is a columnar storage format that supports a document data model, based on Google’s Dremel.

Introduced in “Dremel: Interactive Analysis of Web-Scale Datasets. Communications of the ACM, 2011, 54(6).”

Dremel data model

\[ \tau = \textbf{dom} | \langle A_1: \tau[\ast|?], \dots, A_n: \tau[\ast|?] \rangle \]

  • \(\tau\) is either atomic type or record type
  • \(\textbf{dom}\) includes atomic types: integers, floats, strings, etc.
  • repeated fields (“\(\ast\)”) can occur multiple times, order is important
  • optional fields (“\(?\)”) might be missing
  • fields without (“\(\ast\)”) or (“\(?\)”) are required

Formats: Dremel

Record assembly

  • create a finite state machine (FSM) that reads the field values and levels for each field, and appends the values sequentially to the output records.
  • An FSM state corresponds to a field reader for each selected field.
  • State transitions are labeled with repetition levels.
  • Once a reader fetches a value, we look at the next repetition level to decide what next reader to use.
  • The FSM is traversed from the start to end state once for each record.

Apache Parquet

Formats: Parquet

Parquet at Twitter

Parquet stores nested data structures in a flat columnar format using a technique outlined in the Dremel paper from Google.

Using Parquet at Twitter, we experienced a reduction in size by one third on our large datasets. Scan times were also reduced to a fraction of the original in the common case of needing only a subset of the columns.

Formats: Parquet

Columnar storage advantages

  • better compression (data is more homogenous)
  • reduced I/O will be reduced
  • better encodings suitable for vectorization

LSTs

Why?

Analytical workloads require frequent incremental updates to structured data.

How to solve?

  • add a metadata layer on top of immutable columnar files
  • relegate object store management to a third party (e.g. S3 or MinIO)
  • multi-version concurrency control

LSTs

Metadata

  • stored within file structure of the table
  • commit log of additions/deletions/etc.
  • Copy-on-Write for read-heave scenarios
  • Merge-on-Read for write-heavy scenarios

Iceberg

Table format

The table format acts like a metadata layer on top of the file format and is responsible for specifying how the datafiles should be laid out in storage.

Goals

  • abstract the complexity of the physical data structure
  • facilitate Data Manipulation Language (DML) operations (e.g., doing inserts, updates, and deletes) and changing a table’s schema.
  • add atomicity and consistency guarantees

Iceberg

Storage engine

The storage engine is the system responsible for actually doing the work of laying out the data in the form specified by the table format and keeping all the files and data structures up-to-date with the new data.

Storage engines also handle

  • physical optimization of the data
  • index maintenance
  • getting rid of old data

Iceberg

Catalog

  • The catalog is the central location where compute engines and users can go to find out about the existence of a table, as well as additional information such as the table name, table schema, and where the table data is stored on the storage system.
  • Some catalogs are internal to a system and can only be directly interacted with via that system’s engine; examples of these catalogs include Postgres and Snowflake.
  • Other catalogs, such as Hive and Project Nessie, are open for any system to use.

Iceberg

Compute engine

Compute engine runs user workloads to process the data.

There can be multiple engines.

Massively parallel processing (MPP) engines:

  • Apache Spark
  • Snowflake
  • Dremio.

Iceberg

Iceberg manifest files

Manifest files keep track of files in the data layer (i.e., datafiles and delete files) as well as additional details and statistics about each file, such as the minimum and maximum values for a datafile’s columns.

Each manifest file keeps track of a subset of the datafiles.

  • stored in Avro format
  • lower/upper column bounds
  • record counts
  • partition membership

Iceberg manifest lists

A manifest list is a snapshot of an Iceberg table at a given point in time. It contains:

  • list of all the manifest files
  • locations, partitions, lower/upper bounds for partition columns of tracked datafiles
  • array of structs, with each struct keeping track of a single manifest file.
  • stored in Avro format

Iceberg

Iceberg metadata files

Track manifest lists.

Store metadata about an Iceberg table at a certain point in time

Contain:

  • table schema
  • partition information
    • snapshots, and a pointer to the current one
    • created every time a change is made to the Iceberg table
    • registered atomically via the catalog

Iceberg

  • contain sets of blobs and associated metadata
  • currently support Theta sketches
  • potentially support any index structures (e.g. Bloom filters)
