Data representations

Programs usually work with data in (at least) two different representations:

  • In memory, data is kept in objects, structs, lists, arrays, hash tables, trees, and so on. These data structures are optimized for efficient access and manipulation by the CPU (typically using pointers).
  • When you want to write data to a file or send it over the network, you have to encode it as some kind of self-contained sequence of bytes (for example, a JSON document).

Binary JSON: MessagePack

  • The first byte, 0x83, indicates that what follows is an object (top four bits = 0x80) with three fields (bottom four bits = 0x03)
  • The second byte, 0xa8, indicates that what follows is a string (top four bits = 0xa0) that is eight bytes long (bottom four bits = 0x08)
  • The next eight bytes are the field name userName in ASCII. Since the length was indicated previously, there’s no need for any marker to tell us where the string ends (or any escaping)
  • The next seven bytes encode the six-letter string value Martin with a prefix 0xa6

Thrift/Protobuf: schema evolution

Field tags (1, 2, 3), not names, are written to the bytes. So:

  • a field can be renamed, but its tag can never change
  • a new field gets a new tag and must be optional or have a default (forward compatibility: old code skips unknown tags)
  • only optional fields can be removed, and their tag must never be reused

Lists

Protobuf has no list type: a repeated field is a list. Thrift has a list<...> type, which also allows nested lists.

Avro encoding: 32 bytes

Formats

Avro: writer’s schema vs reader’s schema

The bytes can only be decoded with the exact schema they were written with.

  • the writer’s schema is stored with the data: once in the header of an Avro file, or as a version number in a schema registry (Kafka)
  • the reader’s schema is what the application expects
  • Avro resolves the two by field name: fields missing in the writer’s schema take the reader’s default, and extra fields are ignored

Why it matters

Avro schemas can be generated from a database schema: there are no tags to assign by hand. Avro is used for Kafka messages, Hadoop data, and Iceberg manifests (see below).

Apache Parquet

Formats: Parquet

Parquet at Twitter

Parquet stores nested data structures in a flat columnar format using a technique outlined in the Dremel paper from Google.

Using Parquet at Twitter, we experienced a reduction in size by one third on our large datasets. Scan times were also reduced to a fraction of the original in the common case of needing only a subset of the columns.

Formats: Parquet

Columnar storage advantages

The same as for columnar databases: better compression, reduced I/O, encodings suitable for vectorization. Parquet brings them to files.

Formats: Parquet

File layout

Formats: Parquet

File layout

  • row group: a horizontal slice of the table, typically 64 MB to 1 GB (DuckDB writes 122,880 rows by default)
  • column chunk: the values of one column within one row group, stored contiguously
  • page: the unit of encoding and compression inside a column chunk (about 1 MB)
  • footer: the schema, plus the location and statistics (min, max, null count) of every column chunk. It is written last, so a writer can stream the data first.

Reading a Parquet file

  1. read the footer (the last bytes of the file)
  2. pick the columns the query needs (projection pushdown)
  3. skip the row groups whose min/max cannot match the filter (filter pushdown)
  4. read and decode only the remaining column chunks

Encoding, then compression

Pages are first encoded (lightweight, type-aware), then optionally compressed with a general-purpose codec: Snappy (fast, the old default), zstd (smaller), gzip, LZ4.

Formats: Parquet

Page index: skipping inside a row group

Row-group statistics are coarse: one min/max per ~100,000 rows. The optional page index, stored next to the footer, adds:

  • column index: min/max and null count of every page
  • offset index: where each page starts, so a reader can jump to the matching pages only

Bloom filters: where min/max fails

WHERE user_id = 'u_83412' on a high-cardinality, unsorted column: every row group’s [min, max] contains the value, so nothing is skipped.

A Bloom filter per column chunk answers “definitely not here” or “maybe here”, with no false negatives. Parquet uses split-block Bloom filters: a few KB per column chunk, checked with a few cache-friendly bit tests.

Note

Recall the Bloom filters that LSM engines use to skip SSTables. Same idea, now per file part.

Record assembly

  • create a finite state machine (FSM) that reads the field values and levels for each field, and appends the values sequentially to the output records.
  • An FSM state corresponds to a field reader for each selected field.
  • State transitions are labeled with repetition levels.
  • Once a reader fetches a value, we look at the next repetition level to decide what next reader to use.
  • The FSM is traversed from the start to end state once for each record.

Apache Arrow

Apache Arrow

In-memory columnar format

Parquet is the standard on-disk columnar format. Arrow (2016) is its in-memory counterpart:

  • a column is a contiguous buffer of values, plus a validity bitmap for nulls (and an offsets buffer for strings and lists)
  • data is processed in record batches of columns, the vectors of vectorized execution
  • the same layout in every language: C++, Rust, Java, Python, R, …

Why it matters: zero copy (\(n^2\) problem)

Without a shared format, every exchange between two systems (database \(\rightarrow\) Python, Spark \(\rightarrow\) pandas) means serializing and deserializing every value. With Arrow, systems pass pointers to the same buffers.

DuckDB, Polars, pandas (ArrowDtype; Arrow-backed strings by default since pandas 3.0), Spark (toPandas, pandas UDFs), and Dask can all exchange Arrow tables.

Announced in 2016 as a top-level Apache project, led by es McKinney(creator of pandas) and acques Nadeau(Dremio), together with others.

The Arrow ecosystem

  • Arrow IPC / Feather: Arrow buffers written to a file or stream as they are
  • Arrow Flight: RPC protocol for sending record batches over the network
  • ADBC: a database API (like JDBC/ODBC) that returns Arrow instead of rows

Apache Arrow: memory layout

A string column with a null, as three contiguous buffers:

  • fixed-width types (int64, double, timestamp): just a validity bitmap and one values buffer: value \(i\) is at byte \(8i\), O(1) random access
  • buffers aligned to 64 bytes: ready for SIMD, and for the vectorized execution of the query execution lecture
  • nulls live in the validity bitmap, not in the values:
    • a null still occupies its slot (offsets 4, 4; 8 arbitrary bytes in an int64 column): positions never shift, so access stays O(1) and loops have no special cases
    • no sentinel values: pandas used NaN for missing values, so an int column with a null became float; in Arrow any type can be null, and NaN and null are different things
    • cheap: 1 bit per value (~1.5% of an int64 column), omitted entirely when null_count == 0; filters combine bitmaps 64 rows at a time with bitwise AND/OR
    • contrast with Parquet: no slot for nulls at all, only definition levels. Smaller on disk, but no positional access: storage format vs in-memory format

From arrays to tables

  • array: one column chunk, a set of buffers
  • record batch: a schema + arrays of equal length: the unit that flows between operators and over the wire
  • table: a schema + chunked arrays (a column may consist of many record batches)

Parquet downsides

Parquet was designed in 2013 for HDFS and spinning disks

Large sequential scans of a few columns. Today’s workloads look different:

  • random access: ML training samples random rows, vector search fetches single records. Parquet must decode at least a whole page to read one value.
  • wide tables: ML feature tables have thousands of columns. The Thrift footer must be decoded entirely before reading anything.
  • CPU-bound decoding: on NVMe and fast networks, decompression becomes the bottleneck. Snappy/zstd pages must be decompressed before filtering.
  • SIMD and GPUs: the RLE/bit-packing hybrid decodes value by value, which is hard to vectorize.
  • slow evolution: a new encoding (e.g. ALP) is useful only when every reader supports it, so writers stay with the old ones.

Vortex

Overview

  • created by SpiralDB, donated to the Linux Foundation (LF AI & Data) in August 2025, backed by Microsoft, Snowflake, Palantir, NVIDIA
  • file format stable (backward compatible) since version 0.36
  • readers in DuckDB (core extension), DataFusion, Spark, Trino, Ray; bindings for Rust, Python, Java, C/C++
  • types are Arrow’s: a Vortex array converts to Arrow without copying

Key separation

Logical type (i64, utf8, struct, …) vs physical encoding (how the bytes are laid out). An array is a tree of encodings, and new encodings can be added as plugins.

Vortex: ideas it builds on

Vortex does not invent new compression. It combines published research, much of it from CWI (where DuckDB comes from):

Idea Source What it gives Vortex
FastLanes Afroozeh, Boncz, VLDB 2023 bit-packing, delta, FOR, RLE over vectors of 1,024 values in an interleaved (“transposed”) layout: decoded with simple loops that compilers auto-vectorize on any CPU, and that map well to GPU threads
ALP Afroozeh, Kuffó, Boncz, SIGMOD 2024 doubles that are really decimals → small integers (see the columnar storage slides)
FSST Boncz, Neumann, Leis, VLDB 2020 strings compressed with a symbol table, each string decodable on its own
BtrBlocks Kuschewski et al., SIGMOD 2023 cascading compression: pick the best encoding per block by trying candidates on a sample (~1%), then compress the encoding’s outputs again, recursively. Lightweight encodings only, no zstd.

Compute on compressed data

Because the reader knows the encoding tree, many operations run without decompressing:

  • payment = 'card' on a dictionary: compare 2-bit codes, not strings
  • min/max/count from the arrays’ statistics, trip_id = 42 on a sequence: arithmetic, no data at all
  • filters, projections and expressions are pushed down to the encoded arrays (on CPU, and by design on GPU); values are materialized late, only for rows that survive

Vortex: layouts

A file is a serialized tree of layouts

Parquet fixes the structure: row groups → column chunks → pages. Vortex composes it from generic layouts:

  • struct: one child per column
  • chunked: split rows into parts
  • zoned: a zone map (min, max, …) for every 8,192 rows: finer than Parquet’s row groups
  • dictionary: one dictionary shared by many chunks
  • flat: one serialized array

Consequences

  • default file: struct → zoned → chunked (~2 MB) → compressed → flat. A Parquet-like file is just a different composition.
  • the footer is a FlatBuffer: a reader can jump to one column’s metadata in O(1), without decoding the metadata of the other 9,999 columns
  • extensible: new encodings and layouts are plugins. The design also allows embedding WebAssembly decoders in the file, so old readers can decode new encodings.

import duckdb

work = tempfile.mkdtemp()
con = duckdb.connect()
con.sql("""
SELECT setseed(0.42);
CREATE TABLE trips AS
SELECT i                                                   AS trip_id,
       TIMESTAMP '2025-01-01' + to_seconds(i * 10)         AS pickup_ts,
       (i // 100000)::INTEGER                              AS vendor_id,
       ['cash', 'card', 'app'][1 + (hash(i) % 3)::INTEGER] AS payment,
       1000 + (random() * 50)::INTEGER                     AS zone_id,
       round(random() * 100, 2)                            AS fare
FROM range(1000000) t(i);
""")
con.sql("INSTALL vortex; LOAD vortex;")

vx_files = {
    "v2_snappy.parquet": "(FORMAT parquet, PARQUET_VERSION v2, COMPRESSION snappy)",
    "v2_zstd.parquet":   "(FORMAT parquet, PARQUET_VERSION v2, COMPRESSION zstd)",
    "trips.vortex":      "(FORMAT vortex)",
}
for name, options in vx_files.items():
    con.sql(f"COPY trips TO '{work}/{name}' {options}")
    print(f"{name:18} {os.path.getsize(f'{work}/{name}') / 1e6:4.1f} MB")

ids = ",".join(str(r[0]) for r in con.sql(
    "SELECT (random() * 999999)::BIGINT FROM range(100)").fetchall())
queries = {
    "scan + filter":   "SELECT payment, avg(fare) FROM '{f}' WHERE zone_id < 1010 GROUP BY payment",
    "100 random rows": "SELECT * FROM '{f}' WHERE trip_id IN (" + ids + ")",
}
def best_ms(sql, runs=5):
    times = []
    for _ in range(runs):
        t = time.perf_counter(); con.sql(sql).fetchall(); times.append(time.perf_counter() - t)
    return 1000 * min(times)

for qname, q in queries.items():
    for name in vx_files:
        print(f"{qname:16} {name:18} {best_ms(q.format(f=f'{work}/{name}')):5.1f} ms")

Caveats

  • version 0.x, young ecosystem; most table formats (Iceberg, Delta) still assume Parquet
  • vendor claims (e.g. 100× faster random access) come from the project’s own benchmarks
  • GPU decoding straight from object storage is a goal, not yet the common case

Table formats

Table Format

A table format is a method of structuring a dataset’s files to present them as a unified table.

From the user’s perspective, it can be defined as the answer to the question “what data is in this table?

Goals

  • abstract the complexity of the physical data structure
  • facilitate Data Manipulation Language (DML) operations (e.g., doing inserts, updates, and deletes) and changing a table’s schema.
  • add atomicity and consistency guarantees

LSTs

Why?

Analytical workloads require frequent incremental updates to structured data.

How to solve?

  • add a metadata layer on top of immutable columnar files
  • relegate object store management to a third party (e.g. S3 or MinIO)
  • multi-version concurrency control

LSTs: object storage

What S3 (GCS, Azure Blob, MinIO) gives you

  • immutable objects: write a whole object or replace it. No append, no in-place update, no atomic rename of directories
  • strong read-after-write consistency (S3 since Dec 2020; before that, listings could miss new files)
  • conditional writes (S3 since 2024): “create only if it does not exist” / “replace only if unchanged”: a compare-and-swap
  • cheap storage, but per-request cost and 10–100 ms latency per request

Consequences for table formats

  • every change writes new files: hence log-structured
  • listing a directory is slow and was not consistent: hence an explicit list of files in the metadata, not the directory tree (Hive)
  • atomic commits need one compare-and-swap: a catalog, or a conditional write
  • many small files = many requests: hence compaction

LSTs

Metadata

  • stored within file structure of the table
  • commit log of additions/deletions/etc.
  • Copy-on-Write for read-heavy scenarios
  • Merge-on-Read for write-heavy scenarios

Difference

An LSM tree is a key-value index on one machine. A table format works at the scale of files on object storage. Object storage cannot modify a file in place, so everything has to be append-only.

Delta Lake

Table layout

my_table/
  _delta_log/
    00000000000000000000.json      <- commit 0: add file part-000.parquet
    00000000000000000001.json      <- commit 1: add part-001, remove part-000
    ...
    00000000000000000010.checkpoint.parquet   <- full table state every 10 commits
    _last_checkpoint
  part-000.parquet
  part-001.parquet

How it works

  • each commit is a JSON file of actions: add file (with statistics), remove file, metaData (schema), commitInfo
  • table version \(n\) = replay the log up to \(n\), starting from the latest checkpoint (in Parquet, so readers can use the same Parquet reader)
  • a commit creates file \(n+1\) only if it does not exist yet (put-if-absent): two writers cannot both create version \(n+1\)
  • created at Databricks (2017, open-sourced 2019)

Iceberg

Iceberg architecture

File format

How the data of a single file is encoded:

  • columnar: Parquet, ORC

Analytical table formats store their data in Parquet (most common), ORC or Avro files.

Iceberg

Storage engine

The storage engine is the system responsible for actually doing the work of laying out the data in the form specified by the table format and keeping all the files and data structures up-to-date with the new data.

Storage engines also handle

  • physical optimization of the data
  • index maintenance
  • getting rid of old data

  • The catalog is the central location where compute engines and users can go to find out about the existence of a table, as well as additional information such as the table name, table schema, and where the table data is stored on the storage system.
  • Some catalogs are internal to one system (Postgres, Snowflake); open catalogs can be used by any engine. The Iceberg catalogs are covered below.

Compute engine runs user workloads to process the data.

Massively parallel processing (MPP) engines:

Iceberg manifest files

Manifest files keep track of files in the data layer (i.e., datafiles and delete files) as well as additional details and statistics about each file, such as the minimum and maximum values for a datafile’s columns.

Each manifest file keeps track of a subset of the datafiles.

  • stored in Avro format (see the encoding section): written once, read whole, schema stored in the file
  • lower/upper column bounds
  • record counts
  • partition membership

Two levels of data skipping

A query first skips whole files using the bounds in the manifests, then skips row groups inside the remaining files using the Parquet footers.

Iceberg

Iceberg manifest lists

A manifest list is a snapshot of an Iceberg table at a given point in time. It contains:

  • list of all the manifest files
  • locations, partitions, lower/upper bounds for partition columns of tracked datafiles
  • array of structs, with each struct keeping track of a single manifest file.
  • stored in Avro format

Iceberg

Iceberg metadata files

Track manifest lists.

Store metadata about an Iceberg table at a certain point in time

Contain:

  • table schema (and its history)
  • partition specification
  • list of snapshots, and a pointer to the current one

A new metadata file is created every time the table changes, and it is registered atomically via the catalog.

Iceberg: schema evolution

Columns have IDs

Every column gets a unique field ID in the metadata, and the ID is written into the Parquet schema of each datafile. Readers match columns by ID, not by name or position.

The same idea as the tags of Thrift and Protobuf at the start of the lecture.

What this makes safe

Change Hive-style table (by name or position) Iceberg (by ID)
add a column ok ok, old files return NULL (or the default, v3)
drop, then re-add a column with the same name old values come back new ID: old values stay hidden
rename data disappears (by name) metadata-only
reorder wrong values (by position) metadata-only
widen type (int → long) depends on the reader allowed promotions only

None of these changes rewrites any datafile.

Iceberg: Puffin files

Puffin files

  • store statistics and indexes about the data in the table
  • in addition to stats already in datafile and metadata
  • contain sets of blobs and associated metadata
  • Theta sketches (distinct counts)
  • deletion vectors (Iceberg v3): a bitmap of deleted row positions per datafile
  • potentially any index structure (e.g. Bloom filters)

Iceberg

Theta sketches

Enable more efficient computing of approximate number of distinct values of a column for a given set of rows.

Iceberg

Why not just store distinct counts per file?

Manifests already keep min, max, null count and row count per file. These combine across files: min of mins, sum of counts.

Distinct counts do not: two files with 1,000 distinct customer_ids each can hold anywhere from 1,000 to 2,000 together. This is a non-additive measure (dimensional modeling).

Sketches are mergeable: union the per-file sketches and you get an estimate for the whole table, or any subset of files, without re-reading the data.

Who uses them: the optimizer

The number of distinct values (NDV) drives cardinality estimation, the weak spot of every optimizer (query optimization). This determines join order and the build side of hash joins.

Engines like Trino and Spark write the sketches into Puffin files (e.g. with ANALYZE), so a lakehouse gets the statistics that classic data lakes lacked.

Iceberg

Iceberg catalog

Stores the current location of the current metadata pointer.

Must provide an atomic swap of that pointer.

  • file system (“Hadoop” catalog): a version-hint file; safe only where rename is atomic
  • Hive Metastore, AWS Glue
  • JDBC: any relational database
  • Project Nessie: git-like branches and tags across tables
  • REST catalog: an open HTTP API, now the standard. Implementations: Apache Polaris, Unity Catalog, Lakekeeper, AWS S3 Tables

Iceberg

ACID via optimistic concurrency control

Recall ACID transactions. Iceberg has no lock manager: only the catalog’s atomic pointer swap.

  1. read the current metadata file v3.metadata.json
  2. write new datafiles, manifests, manifest list and v4.metadata.json. Nobody sees them yet.
  3. ask the catalog: “set the pointer to v4 if it still points to v3” (compare-and-swap)
  4. if another writer committed v4 first, the swap fails: re-read, check for conflicts, re-apply the change on top, and retry

Properties

  • atomicity: readers see either the old or the new snapshot, never a mix
  • isolation: snapshot isolation by default, serializable as an option
  • optimistic: cheap when writers rarely touch the same data, many retries when they often do
  • Delta Lake does the same with put-if-absent on the next log file

Branches and tags

A snapshot is just a pointer target, so you can have named pointers, like git:

  • tag: a fixed snapshot kept for a given time, e.g. end-of-year reporting
  • branch: an independent line of snapshots
ALTER TABLE db.trips CREATE TAG eoy_2025 RETAIN 365 DAYS;
ALTER TABLE db.trips CREATE BRANCH audit;

Write-audit-publish (WAP)

  1. the ETL job writes to branch audit; readers of main see nothing
  2. data-quality checks run on audit
  3. if they pass, main is fast-forwarded to audit (CALL catalog.system.fast_forward('db.trips', 'main', 'audit'))

Partitioning: write records with distinct values of the target field into their own datafiles.

Partitioning: Hive-style vs hidden

Hive-style: partitions in the path

trips/year=2025/month=1/data_0.parquet
trips/year=2025/month=2/data_0.parquet

DuckDB, Polars, Spark and Dask read this directly. The engine prunes directories by the key=value names:

COPY (SELECT *, year(pickup_ts) AS year, month(pickup_ts) AS month FROM trips)
  TO 'trips' (FORMAT parquet, PARTITION_BY (year, month));
SELECT count(*) FROM read_parquet('trips/*/*/*.parquet', hive_partitioning = true)
WHERE year = 2025 AND month = 1;

Problems

  • users must filter on year/month, not on pickup_ts, or nothing is pruned
  • changing the scheme means rewriting the table
  • many small partitions → many small files

Iceberg hidden partitioning

The partition spec is a transform of a column, month(pickup_ts), stored in the metadata. A filter on pickup_ts is pruned automatically, and the spec can evolve without rewriting old files. Partitioning across machines comes back with distributed systems.

Table maintenance

The small-files problem

Streaming and frequent small writes create thousands of tiny datafiles and manifests. Every file costs an object-store request, and a footer and a manifest entry to read. Queries get slower even though the data is small.

Regular jobs (Iceberg Spark procedures)

Job Procedure Why
compaction rewrite_data_files merge small files, apply delete files, re-sort
expire snapshots expire_snapshots old snapshots keep old files alive: storage cost, GDPR deletes
remove orphan files remove_orphan_files files written by failed jobs and never committed
rewrite manifests rewrite_manifests regroup manifests so they match the query filters

Note

Expiring snapshots ends time travel to them: choose a retention period (e.g. 7 days).

Iceberg v3 (2025)

New in the v3 spec

  • deletion vectors: one bitmap per datafile in a Puffin file instead of many positional delete files (from Delta Lake)
  • row lineage: each row gets an id and a last-updated sequence number, for incremental processing
  • new types: VARIANT (semi-structured JSON-like data, stored efficiently), geometry/geography, nanosecond timestamps
  • default column values: add a column without rewriting the data

DuckLake

DuckLake

Idea (DuckDB, 2025)

Iceberg and Delta store metadata as files on object storage (JSON, Avro), plus a catalog that only holds one pointer. Every commit writes several files, and every read follows the tree.

DuckLake stores all metadata (snapshots, schemas, file lists, statistics) in a SQL database: DuckDB, SQLite, PostgreSQL or MySQL. The data stays in Parquet files on object storage.

Consequences

  • a commit is one SQL transaction: ACID comes from the database, not from file tricks
  • multi-table transactions, and finding the files of a snapshot with one query
  • small inserts can be inlined into the catalog database, which avoids the small-files problem
  • trade-off: needs a running database for the catalog

Engines on open formats

Apache Spark: architecture

Components

  • driver: runs your program, builds the plan, schedules tasks
  • cluster manager: standalone, YARN, Kubernetes
  • executors: JVM processes on the workers that run tasks, one per data partition, and cache data

Execution: the same model as Dask

  • transformations are lazy: they build a DAG
  • an action (count, write, collect) triggers execution
  • the DAG is cut into stages at shuffles (wide dependencies: groupBy, join)
  • each stage = one task per partition; shuffle files connect stages
  • failure: re-run the lost tasks from lineage, not the whole job

From DataFrame to execution

  1. Catalyst optimizer: logical plan → rule-based rewrites (pushdown, constant folding) → cost-based join selection → physical plan
  2. Tungsten: whole-stage code generation: a stage is compiled into one Java function (query compilation, as in the execution models slides)
  3. Adaptive Query Execution (Spark 3.0): re-optimize between stages using real sizes (coalesce partitions, switch join strategy, split skewed partitions)

The JVM bottleneck and native accelerators

Row-oriented JVM execution with generated code leaves performance on the table compared with vectorized C++/Rust engines. Hence native execution plugged under Spark’s planner:

  • Photon (Databricks, proprietary, C++)
  • Gluten + Velox (Apache, incubating; Velox from Meta, C++)
  • Comet (Apache DataFusion subproject, Rust; donated by Apple)

Spark Connect

Decoupling client and server

Classic PySpark: your Python process is the driver, with a JVM inside. Spark Connect: a thin client sends unresolved logical plans over gRPC; results come back as Arrow batches.

from pyspark.sql import SparkSession

spark = SparkSession.builder.remote("sc://localhost:15002").getOrCreate()
spark.read.parquet("trips.parquet").groupBy("payment").avg("fare").show()

Consequence

The protocol is now the interface, not the JVM. Any engine that speaks Spark Connect can run unmodified PySpark code: this is how Sail works.

Apache DataFusion

A query engine as a library

  • written in Rust, on Arrow memory: started by Andy Grove, donated to Apache Arrow in 2019, top-level Apache project since 2024
  • not a database: no server, no storage of its own. A toolkit to build databases and engines, often called “the LLVM of query engines”
  • SQL and DataFrame front ends → logical plan → optimizer (~30 rules) → physical plan → streams of Arrow record batches, partitioned across CPU cores (Tokio)
  • reads Parquet (with pushdown, page index, Bloom filters), CSV, JSON, Avro, Arrow

Extensible at every level

Custom table providers (your own storage or table format), scalar/aggregate/window UDFs, optimizer rules, physical operators, SQL dialects. You keep what you need and replace the rest.

Sail

Spark API, Rust engine

Sail (LakeSail, open source) is a Spark Connect server built on DataFusion and Arrow. Your PySpark code stays the same, only the session changes:

from pysail.spark import SparkConnectServer   # pip install pysail
from pyspark.sql import SparkSession

server = SparkConnectServer(); server.start()
_, port = server.listening_address
spark = SparkSession.builder.remote(f"sc://localhost:{port}").getOrCreate()

What you gain

  • no JVM: starts in seconds, tens of MB when idle, no garbage-collection pauses or JVM tuning
  • vectorized Arrow execution; Python UDFs run in the same process with zero-copy Arrow data
  • runs locally or distributed on Kubernetes

Caveats

Vendor benchmarks claim ~4–10× faster than Spark on derived TPC-H. Only the DataFrame and SQL API: no RDDs, no MLlib, no Spark packages that need the JVM; streaming is still on the roadmap. A mismatch with Spark’s behaviour is a bug, but there are still some.

Polars

DataFrames, Rust, Arrow memory

Started by Ritchie Vink (2020). Single-node DataFrame library with an expression API, a lazy mode with a query optimizer, and a streaming engine for larger-than-memory data.

import polars as pl

(pl.scan_parquet("trips.parquet")             # lazy: nothing is read yet
   .filter(pl.col("zone_id") < 1010)          # predicate pushdown into the Parquet scan
   .group_by("payment")
   .agg(pl.col("fare").mean())
   .collect())                                # optimize, then execute

Note

Same ideas as the database engines (vectorized execution, projection and predicate pushdown, row-group skipping), with a DataFrame API instead of SQL. Reads Delta (via delta-rs) and Iceberg (via PyIceberg).

Rule of thumb

Most analytical datasets fit on one large machine today. Start with DuckDB or Polars. Move to a cluster engine (Spark, or Sail when its API coverage is enough) when the data or the team’s existing pipelines require it. With open table formats, all of them read the same tables.
