From sequential to parallel

A sequential program is a total order

What the source code says

Statements are written one after another, so they appear to be totally ordered: line 1, then line 2, then line 3.

But most of that order is an artefact of writing the program down. It is not required by the computation.

The real constraint

Statement \(B\) must come after statement \(A\) only if \[ B \text{ reads what } A \text{ wrote.} \] Everything else is free.

Which orderings are actually forced?

Three kinds of dependence

  • true (read-after-write): \(B\) consumes \(A\)’s result — a genuine edge
  • anti (write-after-read): \(B\) overwrites something \(A\) still needs
  • output (write-after-write): \(A\) and \(B\) write the same location

Only the first is about data. The other two come from reusing a name, and disappear if you rename — or never reassign at all.

Which is why

Single-assignment and functional style parallelize more easily: with no reassignment there are no false dependences, and what is left is the dataflow.

From one order to many

From one order to many

What the graph tells us that the listing did not

  • b never needed to wait for a — they can run at the same time
  • d was written after c, but depends only on a; it can run before c, or beside it
  • five statements, but only three levels of real dependence

The shift

The sequential program was one linearization of this graph. Any topological order of the graph computes the same result.

We stop asking “what runs next?” and start asking “what is allowed to run now?”

Choosing the nodes

Granularity is ours to pick

A node can be a single instruction, a loop body, a function call, or “read this 100 MB file”. The theory does not care; the trade-off does:

  • fine grain: more parallelism to exploit, more scheduling overhead per unit of work
  • coarse grain: negligible overhead, less parallelism, worse load balance

We call a node a task and leave its size open for now.

Who recovers the graph?

The same idea, at every level

  • CPUs do it in hardware: out-of-order execution rebuilds the dependence graph over a window of instructions and issues whatever is ready
  • Compilers do it statically: dependence analysis, vectorization, instruction scheduling
  • Build systems are given it: make is a DAG scheduler with files as nodes
  • Parallel frameworks ask you to build it explicitly, then schedule it

From here on

We assume the graph exists. The rest of the lecture is about what to do with it.

Generalization

Multithreaded computing can be viewed as a natural generalization of sequential computing in the following sense:

  • in sequential computing, a computation can be defined as a totally ordered set of instructions, where the ordering corresponds to the sequential execution order;
  • in multithreaded computing, a computation can be viewed as a partially ordered set of instructions (as specified by the DAG), where the instructions may be executed in any order compatible with the specified partial order.

Program as DAG

Ordering re-cap

A binary relation \(\preccurlyeq\) on some set \(X\) is called a partial order if \(\forall a,b,c \in X\) the following is true:

  • Reflexivity: \(a \preccurlyeq a\)
  • Transitiity: \(a \preccurlyeq b, b \preccurlyeq c \Rightarrow a \preccurlyeq c\)
  • Antisymmetricity: \(a \preccurlyeq b, b \preccurlyeq a \Rightarrow a = b\)

If, additionally, \(\forall a,b \ in X\) either \(a \preccurlyeq b\) or \(b \preccurlyeq a\), then the order is total.

Program as DAG

Definitions

A parallel program can be represented by a directed acyclic graph (DAG) \[ G=(V,E), \]

where \(V\) is a set of \(v\) nodes and \(E\) is a set of \(e\) directed edges.

A node in the DAG represents a task which in turn is a set of instructions which must be executed sequentially without preemption in the same processor.

The weight of a node \(n_i\) is called the computation cost and is denoted by \(w(n_i)\).

Program as DAG

Definitions

The edges in the DAG, each of which is denoted by \((n_i,n_j)\), correspond to the communication messages and precedence constraints among the nodes.

The weight of an edge is called the communication cost of the edge and is denoted by \(c(n_i, n_j)\).

The source node of an edge is called the parent node while the sink node is called the child node.

A node with no parent is called an entry node and a node with no child is called an exit node.

The communication-to-computation-ratio (CCR) of a parallel program is defined as its average edge weight divided by its average node weight.

Program as DAG

Definition

Scheduling involves executing a parallel program by mapping the computation over the processors so that:

  • completion time is minimized
  • use of other resources such as storage as energy is optimal.

Program as DAG

Definitions

\(ST(n_i)\) and \(FT(n_i)\) denote start time and finish time at some processor.

After all the nodes have been scheduled, the schedule length is defined as \(\max_i\left\{FT(n_i)\right\}\) across all processors.

The goal of scheduling is to minimize \(\max_i\left\{FT(n_i)\right\}\).

Scheduling is done in such a manner that the precedence constraints among the program tasks are preserved.

Types

  • Static: the characteristics of a parallel program (such as task processing times, communication, data dependencies, and synchronization requirements) are known before program execution
  • Dynamic: a few assumptions about the parallel program can be made before execution, and thus, scheduling decisions have to be made on-the-fly.

Categories

  • Job scheduling: independent jobs are to be scheduled among the processors of a distributed computing system to optimize overall system performance
  • Scheduling and mapping: allocation of multiple interacting tasks of a single parallel program in order to minimize the completion time on the parallel computer system.

Scheduling model variations

Preemptive vs non-preemptive

  • preemptive: execution of the task might be interrupted so that it’s allocated to a different processor
  • non-preemptive: execution must complete on a single processor

Parallel vs non-parallel

Parallel task requires more than one processor for its execution.

With vs without conditional branches

In conditional model, each edge in the DAG is associated with a non-zero probability that the child will be executed immediately after the parent.

Scheduling

List scheduling

The basic idea of list scheduling is to make a scheduling list (a sequence of nodes for scheduling) by assigning them some priorities, and then repeatedly execute the following two steps until all the nodes in the graph are scheduled:

  • Remove the first node from the scheduling list;
  • Allocate the node to a processor which allows the earliest start-time.

Scheduling

Greedy Scheduler

We say that a scheduler is greedy if whenever there is a processor available and a task ready to execute, then it assigns the task to the processor and starts running it immediately. Greedy schedulers have an important property that is summarized by the greedy scheduling principle.

Greedy Scheduling Principle

The greedy scheduling principle postulates that if a computation is run on \(P\) processors using a greedy scheduler, then the total time (clock cycles) for running the computation is bounded by \[ T_P < \frac{W}{P} + S \] where \(W\) is the work of the computation, and \(S\) is the span of the computation (both measured in units of clock cycles).

Scheduling

Optimality of Greedy Schedulers

Firstly, the time to execute the computation cannot be less than \(\frac{W}{P}\) clock cycles since we have a total of \(W\) clock cycles of work to do and the best we can possibly do is divide it evenly among the processors. Secondly, the time to execute the computation cannot be any less than \(S\) clock cycles, because \(S\) represents the longest chain of sequential dependencies. Therefore we have \[ T_P \geq \max\left(\frac{W}{P},S\right). \] We therefore see that a greedy scheduler does reasonably close to the best possible. In particular, \(\frac{W}{P} +S\) is never more than twice \(\max\left(\frac{W}{P} ,S\right)\).

Scheduling

The same bound, other names

The greedy scheduling principle is also known as Brent’s theorem (Brent, 1974) and, in the list-scheduling literature, as Graham’s bound: \[ \max\left(\frac{W}{P}, S\right) \;\leq\; T_P \;<\; \frac{W}{P} + S \;\leq\; 2\max\left(\frac{W}{P}, S\right). \]

Read it as a design rule

Two knobs, and only two: grow the work you can spread (\(W/P\)), shorten the critical path (\(S\)). Everything a scheduler does is fighting for the constant factor between those bounds.

Scheduling

Relation to Amdahl

Amdahl’s law assumes a program splits into a serial fraction \(s\) and a perfectly parallel rest. The DAG model says where \(s\) comes from: it is the span.

  • Amdahl: a number you guess about your program
  • Span: a structural property you can measure, and change, by rewriting the graph

A reduction written as a chain has \(S = \Theta(n)\); written as a tree, \(S = \Theta(\log n)\). Same work, same answer, different ceiling.

How hard is scheduling?

Complexity

The bad news

Minimizing makespan on \(P\) processors under precedence constraints – \(P \mid prec \mid C_{\max}\) – is NP-complete (Ullman, 1975).

It stays NP-complete even when every task takes exactly one time unit – the durations are not what makes it hard, the precedence structure is.

Adding communication costs (\(P \mid prec, c_{ij} \mid C_{\max}\)) makes it NP-hard even with unlimited processors (Papadimitriou & Yannakakis, 1990).

Complexity

The tractable corners

A handful of special cases are solvable exactly in polynomial time:

  • Trees, unit tasks, \(m\) processors – Hu’s level algorithm (1961)
  • Two processors, unit tasks, arbitrary DAG – Coffman–Graham (1972), \(O(v^2)\)
  • Interval orders, unit tasks – Papadimitriou & Yannakakis (1979)

Still open

For a fixed number of processors \(m \geq 3\) with unit tasks and arbitrary precedence, the complexity is still an open problem – one of the oldest in scheduling theory.

Complexity

So why bother with the theory?

Because the approximation results are surprisingly strong.

Graham (1966): any list schedule – no cleverness at all, just “never leave a processor idle if a task is ready” – satisfies \[ \frac{T_{\text{list}}}{T_{\text{opt}}} \leq 2 - \frac{1}{m}. \]

Why it works

At every instant, either all \(m\) processors are busy (we are burning through \(W\)), or some processor is idle – and then a task on a critical path must be running (we are burning through \(S\)).

Complexity

And yet

For independent tasks (no precedence at all), sorting by longest-processing-time-first gives \[ \frac{T_{\text{LPT}}}{T_{\text{opt}}} \leq \frac{4}{3} - \frac{1}{3m} \qquad \text{(Graham, 1969)} \] but the problem is still NP-hard – it contains PARTITION.

Scheduling two identical machines with no dependencies at all is already intractable.

Graham’s anomalies

Graham’s anomalies

The most useful counterexample in scheduling

List scheduling is within a factor of 2. But it is not monotone. Fix the priority list and then make the problem easier: the schedule can get worse.

An instance (Graham, 1969)

Nine tasks, priority list \(L = (T_1, \dots, T_9)\), three processors.

task \(T_1\) \(T_2\) \(T_3\) \(T_4\) \(T_5\) \(T_6\) \(T_7\) \(T_8\) \(T_9\)
time 3 2 2 2 4 4 4 4 9

Graham’s anomalies

Graham’s anomalies: baseline

\(m = 3\), original times, original precedence

\(T_9\) (the long task) is the critical path. One processor idles from \(t=2\) to \(t=4\). This is optimal here.

Anomaly 1: every task gets faster

Subtract 1 from every execution time

Makespan 12 \(\to\) 13. Every single task finished sooner, and the program finished later.

Anomaly 2: add a processor

\(m = 3 \to 4\)

Makespan 12 \(\to\) 15. The fourth processor grabs \(T_4\) early, which releases \(T_5 \dots T_8\) early, which pushes the 9-unit \(T_9\) to the back of the list.

Anomaly 3: remove the dependencies

Drop all precedence constraints

Makespan 12 \(\to\) 16. Fewer constraints, longer schedule.

Graham’s anomalies

The bound on the damage

Graham proved the anomalies are bounded. Going from \(m\) to \(m'\) processors, with the same list: \[ \frac{T_{m'}}{T_m} \leq 1 + \frac{m-1}{m'}. \] So doubling the cluster can never more than roughly halve your gains – but it can absolutely make things worse.

What to take away

  • greedy is within \(2\times\), but not monotone: local improvements are not safe
  • “it got slower after we upgraded” is a legitimate scheduling outcome, not necessarily a bug
  • and all of this assumed exact, known execution times

Scheduling algorithms

Scheduling algorithms

What’s a heuristic algorithm?

Algorithm used when classic methods are too slow for finding an exact or approximate solution, or when classic methods fail to find any exact solution in a search space.

This is achieved by trading

  • optimality,
  • completeness,
  • accuracy,
  • or precision

for speed.

In a way, it can be considered a shortcut.

Scheduling algorithms

List scheduling

A list-scheduling heuristic maintains a list of all tasks of a given graph according to their priorities. It has two phases:

  • the task prioritizing or task selection phase for selecting the highest-priority ready task
  • and the processor selection phase for selecting a suitable processor that minimizes a predefined cost function which can be the execution start time.

Features

  • for a bounded number of fully connected homogeneous processors
  • provide better performance results at a lower scheduling time than the other groups

Scheduling algorithms

Clustering

  • Maps the tasks to unlimited number of clusters. The selected tasks for clustering can be any task, not necessarily a ready task.

  • Each iteration refines the previous clustering by merging some clusters.

  • If two tasks are assigned to the same cluster, they will be executed on the same processor.

Scheduling algorithms

Clustering: Extra final steps

  • a cluster merging step for merging the clusters so that the remaining number of clusters equal the number of processors
  • a cluster mapping step for mapping the clusters on the available processors
  • a task ordering step for ordering the mapped tasks within each processor

Scheduling algorithms

Guided random search

Guided random search techniques (or randomized search techniques) use random choice to guide themselves through the problem space, which is not the same as performing merely random walks as in the random search methods.

These techniques combine the knowledge gained from previous search results with some randomizing features to generate new results.

HEFT/CPOP

Definition

Heterogeneous earliest finish time (HEFT) is a heuristic algorithm to schedule a set of dependent tasks onto a network of heterogeneous workers taking communication time into account.

Critical-Path-On-a-Processor (CPOP) algorithm uses the summation of upward and downward rank values for prioritizing tasks.

H. Topcuoglu, S. Hariri and Min-You Wu, “Performance-effective and low-complexity task scheduling for heterogeneous computing,” in IEEE Transactions on Parallel and Distributed Systems, vol. 13, no. 3, pp. 260-274, March 2002, doi: 10.1109/71.993206.

HEFT/CPOP

Definitions

  • \(V\) – set of \(v\) nodes
  • \(E\) – set of \(e\) edges
  • \(data\) – a \(v \times v\) matrix of communication data
  • \(data_{i,k}\) – amount of data to be transmitted from \(n_i\) to \(n_k\)
  • \(Q\) – set of \(q\) processors
  • \(W\) – a \(v \times q\) computation cost matrix, in which each \(w_{i,j}\) gives the estimated execution cost to complete task \(n_i\) on processor \(p_j\)
  • \(B\) – \(q \times q\) data transfer rates matrix
  • \(L\) – \(q\)-dimensional vector of communication startup costs

HEFT/CPOP

Costs

Average execution cost: \[ \overline{w_i} = \sum\limits_{j=1}^q \frac{w_{i,j}}{q}. \] Communication cost of the edge \((i,k)\) for transfering data from task \(n_i\) scheduled on processor \(p_m\) to task \(n_k\) scheduled on processor \(p_n\): \[ c_{i,k} = L_m + \frac{data_{i,k}}{B_{m,n}} \] Average communication cost: \[ \overline{c_{i,k}} = \overline{L} + \frac{data_{i,k}}{\overline{B}} \]

HEFT/CPOP

Times

Earliest execution start time of task \(n_i\) on processor \(p_j\): \[ \begin{align*} & EST(n_{entry}, p_j) = 0, \\ & EST(n_i, p_j) = \max\left\{avail[j], \max\limits_{n_m \in pred(n_i)} (AFT(n_m)+c_{m,i})\right\}, \end{align*} \] where \(avail[j]\) is the earliest time at which processor \(p_j\) is ready for task execution.

Earliest execution finish time of task \(n_i\) on processor \(p_j\): \[ EFT(n_i, p_j) = w_{i,j} + EST(n_i,p_j) \]

After a task \(n_m\) is scheduled on processor \(p_j\), the earliest start time and the earliest finish time of \(n_m\) on processor \(p_j\) is equal to the actual start time \(AST(n_m)\) and the actual finish time \(AFT(n_m)\), respectively.

HEFT/CPOP

Workspan

After all tasks in the graph have been scheduled, the schedule length (makespan) will be equal to the actual finish time of the exit task \(n_{exit}\). In case of several exits: \[ makespan = \max \left\{AFT(n_{exit})\right\} \]

Definition

The objective function of the task scheduling problem is to determine the assignment of tasks to processors such that its makespan is minimized.

HEFT/CPOP

Upward rank

\[ \begin{align*} rank_u(n_i) = \overline{w_i} + \max\limits_{n_j \in succ(n_i)} \left(\overline{c_{i,j}} + rank_u(n_j)\right) \end{align*} \]

  • \(succ(n_i)\) – set of immediate successors of \(n_i\)
  • \(\overline{c_{i,j}}\) – average communication cost of edge \((i,j)\)
  • \(\overline{w_i}\) – average computation cost of task \(n_i\)

\[ rank_u(n_{exit}) = \overline{w_{exit}} \]

HEFT/CPOP

Downward rank

\[ \begin{align*} rank_d(n_i) = \max\limits_{n_j \in pred(n_i)} \left(rank_d(n_j)+ \overline{w_j} + \overline{c_{j,i}}\right) \end{align*} \]

  • \(pred(n_i)\) – set of immediate predecessors of \(n_i\)
  • \(rank_d(n_{entry}) = 0\)
  • can be thought of as the longest distance from the entry task to \(n_i\) without computation costs

HEFT/CPOP

HEFT

  1. Set the computation costs of tasks and communication costs of edges with mean values
  2. Compute \(rank_u\) for all tasks by traversing graph upward, starting from the exit task
  3. Sort the tasks in the scheduling list by non-increasing order of \(rank_u\) values
  4. while there are unscheduled tasks in the list do:
  5.    select the task \(n_i\) from the scheduling list
  6.    for each processor \(p_k\) in the processor set \(Q\) do:
  7.      Compute \(EFT(n_i,p_k)\) using the insertion-based scheduling policy
  8.    Assign task \(n_i\) to the processor \(p_j\) minimizing \(EFT(n_i, p_j)\)

HEFT/CPOP

CPOP

  1. Set the computation costs of tasks and communication costs of edges with mean values
  2. Compute \(rank_u\) for all tasks by traversing graph upward, starting from the exit task
  3. Compute \(rank_d\) for all tasks by traversing graph downward, starting from the entry task
  4. Compute \(priority(n_i) = rank_d(n_i) + rank_u(n_i) \; \forall n_i\)
  5. \(|CP| = priority(n_{entry})\)
  6. \(SET_{CP} = \{n_{entry}\}\), where \(SET_{CP}\) is a set of tasks on a critical path
  7. \(n_k \leftarrow n_{entry}\)

HEFT/CPOP

CPOP

  1. while \(n_k \neq n_{exit}\) do
  2.    select \(n_j: n_j \in succ(n_k) \textbf{ and } priority(n_j) = |CP|\)
  3.    \(SET_{CP} = SET_{CP} \cup {n_j}\)
  4.    \(n_k \leftarrow n_j\)
  5. select \(p_{CP}\) minimizing \(\sum\limits_{n_i \in SET_{CP}} w_{i,j} \; \forall p_j \in Q\)
  6. initialize priority queue \(PQ\) with the entry task

HEFT/CPOP

CPOP

  1. while there are unscheduled tasks in the \(PQ\)do
  2.    select the highest priority task \(n_i\) from \(PQ\)
  3.    if \(n_i \ in SET_{CP}\) then
  4.      assign \(n_i\) to \(p_{CP}\)
  5.    else
  6.      assign \(n_i\) to \(p_j\) minimizing \(EFT(n_i,p_j)\)
  7.    update \(PQ\) with the successors of \(n_i\) if ready

Dynamic scheduling

Why the static picture breaks

HEFT needs a cost matrix. Where would you get one?

Static algorithms want \(w(n_i, p_k)\) and \(c(n_i, n_j)\) for every task and every processor, before anything runs. In a real analytics cluster:

  • a task’s duration depends on data it has not read yet (how many rows survive a filter?)
  • the machine is shared – noisy neighbours, thermal throttling, a cold page cache
  • the first execution of a task includes JIT warm-up and import time
  • workers appear and disappear (autoscaling, spot instances, OOM kills)
  • \(c(n_i,n_j)\) is \(0\) if the data is already on the worker and seconds if it is not – which is what you are trying to decide

Why the static picture breaks

And the graph itself may not be finished

  • dask.dataframe does not know partition sizes until it reads them
  • shuffles produce graph structure that depends on the data
  • interactive work appends to the graph while earlier parts are still running

The pivot

Stop computing a schedule. Compute a policy: a cheap rule, re-evaluated constantly, that is good on average and recovers from being wrong.

Work sharing vs work stealing

Two ways to balance load

  • Work sharing: whenever a processor creates new work, it pushes it out to a central pool or to another processor. Migration happens whenever work is created.
  • Work stealing: an idle processor pulls work from a busy one. Migration happens only when a processor runs dry.

Why stealing wins

When everybody is busy, stealing costs nothing at all: no messages, no contention. Communication is proportional to the imbalance, not to the amount of work.

The deque discipline

The deque discipline

Why the two ends differ

  • The owner runs its own deque LIFO. That is a depth-first traversal: the data it needs is the data it just produced, still in L1/L2. It also keeps the memory footprint small (see dask.order later).
  • The thief takes from the other end, FIFO. The oldest entry sits nearest the root of the computation, so it is usually the largest remaining subtree. One expensive steal buys a long stretch of local work.
  • Because the two ends are different, owner and thief almost never touch the same slot – the common path needs no lock at all (Cilk’s THE protocol).

Work stealing: the theory

Blumofe & Leiserson (1999)

For a fully strict computation with work \(T_1\) and span \(T_\infty\), randomized work stealing on \(P\) processors achieves \[ \mathbb{E}[T_P] \;=\; \frac{T_1}{P} + O(T_\infty) \] – provably within a constant factor of optimal, with no knowledge of task durations at all.

And two bounds that matter more in practice

  • Space: \(S_P \leq P \cdot S_1\) – stealing cannot blow up memory more than linearly in \(P\)
  • Communication: expected \(O(P \, T_\infty \, S_{\max})\) bytes – again proportional to the span, not the work

Work stealing: the theory

Why random victim selection?

A thief picks a victim uniformly at random. No load table, no coordination, no central state.

If a constant fraction of the deques are non-empty, a steal succeeds with constant probability, so \(O(P)\) steal attempts suffice per unit of progress. Any attempt to be smarter reintroduces the shared state you were trying to avoid.

The work-first principle (Cilk)

Move overhead off the work path and onto the critical path. The work path executes \(T_1\) times; the steal path executes \(O(P\,T_\infty)\) times. Make the common case free, and let stealing be expensive.

Locality vs load balance

The core tension

Two jobs pull in opposite directions:

  • balance: keep every processor busy \(\Rightarrow\) move tasks freely
  • locality: run a task where its input already is \(\Rightarrow\) never move tasks

Moving a task is cheap. Moving its 200 MB input is not.

Delay scheduling (Zaharia et al., 2010)

When the next task’s preferred node is busy: wait a few seconds instead of launching it elsewhere. Slots free up constantly, so a short wait almost always wins the local slot.

In the Hadoop fair scheduler this raised data locality to nearly 100% and roughly doubled throughput. Five lines of policy.

Sampling instead of state

The power of two choices

Placing a task on a uniformly random worker of \(n\) leaves a maximum queue length of \(\Theta(\log n / \log\log n)\).

Sampling two at random and taking the shorter queue drops it to \(\Theta(\log\log n)\) – an exponential improvement, for one extra probe.

Why schedulers care

It means you can get near-centralized quality of placement with no centralized state at all. Sparrow builds a whole distributed scheduler out of this idea: batch sampling plus late binding – place reservations on several workers, and let the first one to become free actually claim the task.

Stragglers

The task that will not finish

In a 10 000-task stage, the makespan is set by the slowest task, not the average one. Causes: a bad disk, a hot node, skewed data, a background daemon, a garbage collection pause.

Speculative execution: once a stage is nearly done, launch duplicate copies of the laggards and take whichever finishes first.

Refinements

  • MapReduce (2004): back up the last few tasks near the end of a phase
  • LATE (2008): rank by longest approximate time to end, not by progress so far – crucial on heterogeneous nodes
  • Mantri (2010): diagnose the cause (data skew vs slow node) before acting
  • Dolly (2013): for small jobs, just clone every task up front – cheaper than detecting stragglers

Stragglers

The tail at scale (Dean & Barroso, 2013)

If a single machine answers within 10 ms 99% of the time, then a request that fans out to 100 machines waits longer than 10 ms 63% of the time.

Rare slowness at the component level becomes the common case at the system level.

Techniques

hedged requests (send a second copy after the 95th-percentile delay), tied requests (send two, have them cancel each other), micro-partitioning, selective replication, “good enough” partial answers.

The scheduler is itself a parallel program

Costs you now own

  • a decision must be cheaper than the task it schedules – so per-task overhead sets your minimum useful task size
  • the scheduler holds state proportional to the graph, not the cluster: millions of tasks means millions of objects in one process
  • every policy above (stealing, speculation, locality delay) is work the scheduler does while jobs are running
  • and each one can misfire: stealing can thrash, speculation can double your cluster load, locality delay can idle machines

Beyond one framework

Who hands out the machines?

Two levels of scheduling

Everything so far was intra-job: one framework deciding which of its tasks runs on which of its workers.

But those workers are processes on machines that somebody else hands out — to this job and to fifty other tenants at the same time. That is cluster resource management, and it is a second, mostly independent scheduling problem.

Why it is harder, not easier

  • jobs arrive online, with no notice and no cost estimates
  • multiple resource dimensions: CPU, memory, disk, network, GPUs, licences
  • fairness and priorities across teams that do not trust each other
  • long-running services and batch jobs sharing the same machines
  • decisions must be made in milliseconds, at tens of thousands of machines

Four architectures

Four architectures

The trade-off in one line

Going down the list, you trade decision quality for decision throughput.

  • monolithic: best decisions, one bottleneck, and every new policy goes into the same codebase
  • two-level: isolation between frameworks – but a framework can only reason about the slice it was offered
  • shared state: everyone sees everything and commits transactions; conflicts are resolved by retrying, which is fine until contention is high
  • distributed: millisecond decisions at any scale, and no way to enforce a global policy

Fairness with many resources

What does “half the cluster” even mean?

User A’s jobs are CPU-bound; user B’s are memory-bound. Splitting cores evenly wastes memory; splitting memory evenly wastes cores.

Dominant Resource Fairness (Ghodsi et al., 2011): for each user, find the resource of which they consume the largest share – their dominant resource – and equalize those shares.

Why it caught on

DRF is strategy-proof (lying about your needs does not help), envy-free, and Pareto-efficient. It is the default in Mesos and in YARN’s capacity scheduler.

Even “be fair” turns out to be a research problem.

Scale, for perspective

The numbers

  • a Borg cell: tens of thousands of machines, one logically centralized scheduler
  • Google reported Borg placing on the order of 10 000 tasks per minute per cell
  • Sparrow targets sub-second tasks with millisecond placement decisions, spread over many independent schedulers
  • a Dask scheduler: a few thousand tasks per second, single-threaded Python

Different problems, four orders of magnitude apart in task size.

The honest summary

What “scheduling” turned out to mean

We started with a clean statement – minimize \(\max_i FT(n_i)\) over a weighted DAG – and found:

  1. it is NP-complete, and stays so under almost every simplification
  2. the trivial greedy algorithm is already within \(2\times\) of optimal
  3. …but is not monotone: more processors can be slower
  4. the inputs it needs (durations, communication costs) do not exist at run time
  5. so real systems measure instead, and re-decide continuously
  6. and then spend most of their code on memory, failure, elasticity and observability – none of which appear in the model at all

The honest summary

Where the theory still earns its keep

  • work and span tell you the ceiling before you write any code
  • Graham’s bound says a simple greedy policy is not the thing holding you back
  • Graham’s anomalies say to measure, not to reason, about “improvements”
  • list scheduling’s two phases – pick a task, pick a processor – are exactly the two halves of every real scheduler: a static ordering pass and a placement rule
  • work stealing’s bounds are why the decentralized version is respectable and not a hack

The practical rule

Your job is to hand the scheduler a graph it can do well on: few enough tasks, big enough tasks, short enough span, small enough intermediates.
