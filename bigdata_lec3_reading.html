1. From a program to a graph

The source code lies about the ordering

A sequential program is a total order: statement 1, then 2, then 3. But that total order is an artefact of how we had to write it down. Most of it is not required by the computation.

a = f(1)
b = g(2)
c = h(a, b)
d = k(a)
e = m(c, d)

Five statements in a line, but b never needed to wait for a, and d — written after c — depends only on a, so it could run before c, or beside it. The real structure is a graph with only three levels of genuine dependence. The sequential listing was one linearization of that graph, and any topological order of the graph computes the same answer.

That is the shift the whole lecture rests on. We stop asking “what runs next?” and start asking “what is allowed to run now?”

Which orderings are actually forced

The answer is old and precise. In 1966 A. J. Bernstein1 asked exactly this question — when may two successive parts of a program run in parallel and still produce the same result? — and gave three conditions. Writing \(I_i\) for the locations statement \(i\) reads and \(O_i\) for those it writes, two statements are independent when

\[I_1 \cap O_2 = \emptyset \qquad I_2 \cap O_1 = \emptyset \qquad O_1 \cap O_2 = \emptyset\]

Each violated condition is one kind of dependence:

kind pattern forced?
true (flow) read-after-write: \(B\) consumes \(A\)’s result yes — a genuine edge
anti write-after-read: \(B\) overwrites what \(A\) still needs no — an artefact of reusing a name
output write-after-write: both write the same location no — likewise

Only the first is about data. The other two exist because we reused a name, and they vanish if you rename the variable. This is why they are called false or name dependences, and why hardware bothers to undo them: Tomasulo’s algorithm (1967)2 is register renaming in silicon, and every out-of-order CPU since does the same thing.

To see how cheap the fix is, here is a fragment with all three kinds at once:

x = load()        # S1
y = f(x)          # S2   true dep on S1   (S2 reads what S1 wrote)
x = g()           # S3   anti dep on S2   (S3 overwrites x, which S2 reads)
z = h(x)          # S4   true dep on S3
x = k(z)          # S5   output dep on S3 (both write x)

S3 cannot move above S2, and S5 cannot move above S3 — but neither restriction has anything to do with the computation. Rename and they evaporate:

x1 = load()       # S1
y  = f(x1)        # S2   depends on S1
x2 = g()          # S3   depends on nothing --- free to run first, or in parallel
z  = h(x2)        # S4   depends on S3
x3 = k(z)         # S5   depends on S4

Now S1 → S2 and S3 → S4 → S5 are two independent chains, and the span has dropped from 5 to 3. Nothing about the computation changed; we only stopped recycling the name x.

It is also the reason single-assignment and functional style parallelize more easily. If you never reassign, there are no false dependences to begin with, and what remains is the dataflow. SSA form in compilers3 is the same trick applied universally.

Note

The terminology (flow / anti / output) and the dependence graph as a compiler data structure come from David Kuck’s group at Illinois.4 Adding control dependence to the picture gives the program dependence graph.5

Choosing the nodes

Nothing so far says how big a node is. It can be one instruction, a loop body, a function call, or “read this 100 MB file”. The theory does not care. The trade-off does:

  • fine grain — more parallelism available, more scheduling overhead per unit of work
  • coarse grain — negligible overhead, less parallelism, worse load balance

We call a node a task and leave its size open. Where you set that dial is one of the few decisions that is genuinely yours; the scheduler’s per-task overhead sets a hard floor on how small a useful task can be.

It helps to have orders of magnitude in mind. A hardware instruction is sub-nanosecond. A function call is nanoseconds. A Python-level task in a distributed scheduler costs on the order of hundreds of microseconds to a millisecond of bookkeeping — graph entry, dependency tracking, serialisation, a message or two. So a task that does 200 µs of real work spends more time being scheduled than running, and a job of a million such tasks spends longer in the scheduler than in your code.

The rule of thumb that follows: aim for tasks in the 100 ms to a few seconds range. Below that, overhead dominates; far above it, you lose load balance and you lose the ability to recover cheaply from a failure. When people complain that a distributed framework is “slow”, the cause is very often a graph with a million tiny nodes, not a slow framework.

This is also the first place the theory bites. Making tasks smaller increases available parallelism (lowers \(S\) relative to \(W\)) but adds overhead to \(W\). There is an optimum, and it is not at either extreme.

Who recovers the graph?

The same idea appears at every level of the stack, which is a good sign it is the right idea:

  • CPUs rebuild it in hardware — out-of-order execution reconstructs the dependence graph over a window of instructions and issues whatever is ready
  • Compilers build it statically — dependence analysis, vectorization, instruction scheduling
  • Build systems are handed it — make is a DAG scheduler with files as nodes
  • Parallel frameworks ask you to build it explicitly, then schedule it

2. Work, span, and why greedy is good enough

Two numbers describe a computation

For a DAG where each node has a cost:

  • work \(W\) — the total cost of all nodes. What one processor would do.
  • span \(S\) — the cost of the longest path. What infinitely many processors could not avoid.

Both are properties of the graph, independent of how many machines you own.

Computing them

Both are straightforward graph computations. Span is the longest path, which on a DAG is a single pass in topological order:

def work(cost):
    return sum(cost.values())

def span(preds, cost):
    """Longest cost-weighted path ending at any node."""
    memo = {}
    def longest_to(n):
        if n not in memo:
            memo[n] = cost[n] + max([longest_to(p) for p in preds[n]], default=0)
        return memo[n]
    return max(longest_to(n) for n in preds)


# the five-statement example from section 1, one unit each
preds = {"a": [], "b": [], "c": ["a", "b"], "d": ["a"], "e": ["c", "d"]}
cost  = {k: 1 for k in preds}

W, S = work(cost), span(preds, cost)
print(f"W = {W}, S = {S}, parallelism W/S = {W/S:.2f}")
W = 5, S = 3, parallelism W/S = 1.67

So the little example has work 5 and span 3 — the chains \(a \to c \to e\) and \(a \to d \to e\) both cost 3. Note what this says: no number of processors will ever run this in less than 3 units, and more than about 2 processors is wasted on it.

The greedy bound

A scheduler is greedy if it never leaves a processor idle while some task is ready. That is the whole rule — no lookahead, no cleverness. Remarkably, it is almost enough:

\[T_P < \frac{W}{P} + S\]

The argument is two lines. Consider any instant. Either all \(P\) processors are busy, in which case we are consuming work at the maximum rate and there can be at most \(W/P\) such time; or some processor is idle, which for a greedy scheduler means nothing was ready, which means some task on a critical path is running, and there can be at most \(S\) such time. Add them.

And no schedule can beat

\[T_P \geq \max\!\left(\frac{W}{P},\, S\right)\]

since you cannot do the work faster than dividing it evenly, nor finish before the longest chain has run. Because \(\frac{W}{P} + S\) is never more than twice \(\max(\frac{W}{P}, S)\), any greedy scheduler is within a factor of 2 of optimal.

This result has three names depending on which literature you are reading: the greedy scheduling principle, Brent’s theorem (1974),6 or Graham’s bound7. They are the same statement.

\[\max\!\left(\frac{W}{P}, S\right) \;\leq\; T_P \;<\; \frac{W}{P} + S \;\leq\; 2\max\!\left(\frac{W}{P}, S\right)\]

When is the bound tight?

That factor of 2 is not an artefact of a loose proof — it is achievable. The worst case looks like this: a long critical chain, plus just enough independent work to keep every processor busy right up until the chain must run alone. Greedy happily fills the processors first, then discovers the chain still has to execute serially at the end.

That shape is exactly what Graham’s anomalies in Section 4 exploit, and it is also why a scheduler that knows the critical path (the “upward rank” of Section 5) can beat a naive one in practice even though both are within the same factor of 2.

Parallelism, speedup, efficiency

Three derived quantities are worth naming, because people use them constantly and sometimes loosely:

quantity definition reading
parallelism \(W / S\) the maximum useful number of processors
speedup \(T_1 / T_P\) how much faster \(P\) processors actually made it
efficiency \(T_1 / (P \cdot T_P)\) what fraction of the hardware you are wasting

Parallelism is the one to internalise. It is a property of the graph alone. If \(W/S = 4\), then buying a 64-core machine cannot help you past 4 cores, no matter how good the scheduler is; and the greedy bound says that once \(P \ll W/S\) you get close to linear speedup almost for free. Both halves of that sentence are useful.

Read it as a design rule

There are exactly two knobs: grow the work you can spread (\(W/P\)), and shorten the critical path (\(S\)). Everything any scheduler does is fighting over the constant factor between those two bounds. If you want a faster parallel program, changing the graph beats changing the scheduler.

Where Amdahl’s serial fraction comes from

Amdahl’s law assumes a program splits into a serial fraction \(s\) and a perfectly parallel remainder. The DAG model tells you what \(s\) is: it is the span.

  • Amdahl’s \(s\): a number you estimate about your program.
  • Span: a structural property you can measure, and change, by rewriting the graph.

The canonical example: a reduction written as a chain has \(S = \Theta(n)\); written as a tree it has \(S = \Theta(\log n)\). Same work, same answer, completely different ceiling on how much hardware can help.

\(n\) work chain span tree span max useful processors (tree)
8 7 7 3 ~2
1 024 1 023 1 023 10 ~102
1 000 000 999 999 999 999 20 ~50 000

sum(xs) in a loop is the first column. functools.reduce is the first column. A pairwise tree reduction — which is what every parallel framework does internally, and incidentally what math.fsum and NumPy’s pairwise summation do for accuracy reasons — is the second. The work is identical. The ceiling differs by four orders of magnitude.

This is the single most useful thing in the lecture: when a parallel program will not go faster, look at the span before you look at the scheduler.

A footnote on Amdahl and Gustafson

Amdahl’s 1967 argument8 is often read as pessimism about parallel computing, and Gustafson’s 1988 reply9 as the optimistic correction. The difference is what you hold fixed:

  • Amdahl fixes the problem and adds processors. The serial part does not shrink, so speedup saturates at \(1/s\).
  • Gustafson fixes the time budget and asks how much bigger a problem you can solve. The parallel part grows with the machine, so the serial fraction shrinks in relative terms.

In DAG language: Amdahl asks what happens to \(T_P\) for a fixed graph as \(P\) grows; Gustafson observes that in practice people grow the graph when they get a bigger machine, and growing \(W\) while \(S\) stays put is exactly what makes parallelism \(W/S\) increase. Both are right about their own question.

3. How hard is the scheduling problem?

A terminological note first, because the two words get used interchangeably: the decision problem (“is there a schedule of length \(\leq k\)?”) is NP-complete; the optimization problem (“find the shortest schedule”) is NP-hard. The slides say NP-complete where they quote Ullman’s title; both refer to the same difficulty. This document says NP-hard throughout.

Given the DAG and the costs, finding the optimal schedule is NP-hard in almost every variant that matters. A few corners are tractable (two processors with unit tasks; tree-shaped precedence graphs), and one famous case — fixed \(m \geq 3\) with unit tasks and arbitrary precedence — has been open for decades.

How to read the problem names

The scheduling literature classifies problems with a three-field notation, \(\alpha \mid \beta \mid \gamma\), introduced by Graham, Lawler, Lenstra and Rinnooy Kan.10 You will meet it in any paper on the subject and it is worth five minutes:

field meaning common values
\(\alpha\) machine environment \(1\) (single), \(P\) (identical parallel), \(Q\) (uniform, different speeds), \(R\) (unrelated)
\(\beta\) job characteristics prec (precedence constraints), \(p_j = 1\) (unit times), pmtn (preemption allowed), r_j (release dates)
\(\gamma\) objective \(C_{\max}\) (makespan), \(\sum C_j\) (total completion time), \(L_{\max}\) (lateness)

So \(P \mid\mid C_{\max}\) is “identical parallel machines, no special constraints, minimise makespan” — the problem in the next subsection. \(P \mid \text{prec}, p_j{=}1 \mid C_{\max}\) is the unit-task precedence-constrained version, and \(P2 \mid\mid C_{\max}\) fixes two machines.

The tractable corners

A handful of cases are solvable exactly in polynomial time, and they are worth knowing because they mark the boundary:

  • \(P \mid \text{tree}, p_j{=}1 \mid C_{\max}\) — unit tasks whose precedence graph is a tree. Hu’s algorithm (1961)11 solves this optimally for any number of processors, by scheduling in order of height in the tree.
  • \(P2 \mid \text{prec}, p_j{=}1 \mid C_{\max}\) — unit tasks, arbitrary precedence, exactly two processors. Coffman–Graham (1972)12 is optimal here, in \(O(v^2)\).
  • Interval orders, unit tasks — Papadimitriou & Yannakakis (1979)13. An interval order is a precedence graph you can draw as intervals on a line, with \(a \prec b\) when \(a\) ends before \(b\) begins; that extra structure is enough to make the problem tractable.
  • Most other variants are NP-hard; Ullman (1975)14 established several of the key completeness results.

And the famous gap: for a fixed \(m \geq 3\) with unit tasks and arbitrary precedence, whether the problem is in P or NP-hard has been open since the 1970s. It is one of the longest-standing open problems in scheduling.

And it gets worse once communication enters the model: adding communication costs (\(P \mid \text{prec}, c_{ij} \mid C_{\max}\)) makes the problem NP-hard even with unlimited processors (Papadimitriou & Yannakakis, 1990).15 You cannot buy your way out of it with hardware.

The pattern is instructive. Hardness arrives as soon as you allow either arbitrary task durations, or a third processor with an arbitrary graph, or communication costs. Almost everything you would actually want to schedule is on the wrong side of that line.

“It contains PARTITION”

The slides say that scheduling independent tasks is still NP-hard because it “contains PARTITION”. That phrase means: PARTITION is a special case, so an algorithm for this would solve PARTITION too.

PARTITION (one of Karp’s 21, 1972)16: given positive integers \(a_1, \dots, a_n\), can they be split into two groups with equal sums?

The reduction is essentially the identity. Take a PARTITION instance with total \(T = \sum a_i\). Build a scheduling instance: \(m = 2\) machines, \(n\) independent tasks, \(p_i = a_i\). Then the makespan is at least \(T/2\) (that is just total work over two machines), and it equals \(T/2\) exactly when the tasks split into two groups of \(T/2\) each. So “is \(C_{\max} \leq T/2\)?” is PARTITION in disguise.

Two identical machines, no dependencies at all, and the problem is already intractable.

But the mildest kind of intractable

This looks like it contradicts the good approximation results, and the resolution is worth knowing. PARTITION is only weakly NP-complete: a pseudo-polynomial \(O(nT)\) dynamic program solves it17. The hardness comes from the numbers being large, not from combinatorial structure. Consequently:

  • \(P2 \mid\mid C_{\max}\) admits an FPTAS (Sahni, 1976)18 — which is why a rule as crude as longest-processing-time-first already lands within \(\frac{4}{3} - \frac{1}{3m}\).
  • With \(m\) part of the input, \(P \mid\mid C_{\max}\) becomes strongly NP-hard via 3-PARTITION19. A PTAS still exists (Hochbaum & Shmoys, 1987).20

The bounds are not just asymptotic comfort

It is worth seeing how small the gap actually is on a concrete instance. Six independent tasks with durations \((3,3,2,2,2,2)\) on three processors:

  • the optimal makespan is 5;
  • longest-processing-time-first also achieves 5;
  • the worst possible list achieves 6;
  • Graham’s general guarantee allows up to \((2 - \frac{1}{3}) \times 5 = 8.33\);
  • the LPT guarantee allows up to \((\frac{4}{3} - \frac{1}{9}) \times 5 = 6.11\).

So the theoretical worst case is a factor of 1.67, the achievable worst case on this instance is 1.2, and a two-line sorting rule gets it exactly right. That ratio — theory pessimistic, practice fine — is typical, and it is why real systems use list scheduling and spend their effort elsewhere.

So: NP-hard, yes — but the easiest flavour of it. In practice nobody agonises over list scheduling, and this is why.

4. Graham’s anomalies

This is the section that does not compress well, so here it is at length.

Where they came from

Ron Graham was at Bell Labs in the mid-1960s, when multiprocessing systems were new and people were making entirely reasonable-sounding predictions about them: buy a faster machine and your job finishes sooner; add a processor and your job finishes sooner; remove an artificial ordering constraint and your job finishes sooner.

Graham showed all three are false, using one nine-task example, and then proved bounds on how false they can be. The results appear in two papers:

  • R. L. Graham, Bounds for certain multiprocessing anomalies, Bell System Technical Journal, 196621
  • R. L. Graham, Bounds on multiprocessing timing anomalies, SIAM J. Applied Mathematics, 196922

The anomalies are not a curiosity about a contrived example. They are the reason “we upgraded the cluster and it got slower” is a legitimate outcome rather than automatically a bug.

The setup

Nine tasks, three processors, list scheduling with the fixed priority list \(L = (T_1, T_2, \dots, T_9)\).

task \(T_1\) \(T_2\) \(T_3\) \(T_4\) \(T_5\) \(T_6\) \(T_7\) \(T_8\) \(T_9\)
time 3 2 2 2 4 4 4 4 9

Precedence: \(T_1 \to T_9\), and \(T_4 \to T_5, T_6, T_7, T_8\). Tasks \(T_2\) and \(T_3\) are free.

The rule is the simplest possible: whenever a processor falls idle, give it the earliest task in \(L\) whose predecessors have all finished. Nothing else changes between the four scenarios below — same list, same rule.

Two features of this instance do all the work, and everything that follows is a consequence of them:

  1. \(T_9\) is by far the longest task (9 units against 2–4 for everything else).
  2. \(T_9\) is last in the priority list.

So whenever another task is ready at the same moment as \(T_9\), the other task wins the processor, and the long task gets pushed later. Anything that makes the other tasks available earlier hurts.

Reproducing it

def list_schedule(times, preds, m, order):
    """Non-preemptive list scheduling: whenever a processor is free, start the
    highest-priority READY task (one whose predecessors have all finished)."""
    n = len(times)
    start, finish, assign = [None] * n, [None] * n, [None] * n
    free = [0.0] * m               # time at which each processor becomes free
    running, done, t = [], set(), 0.0

    while len(done) < n:
        progressed = True
        while progressed:          # fill every idle processor at the current time
            progressed = False
            for p in range(m):
                if free[p] <= t:
                    for i in order:
                        ready = all(q in done for q in preds.get(i, []))
                        if start[i] is None and ready:
                            start[i], finish[i] = t, t + times[i]
                            free[p], assign[i] = finish[i], p
                            running.append((finish[i], i))
                            progressed = True
                            break
                    if progressed:
                        break
        nxt = min((f for f, i in running if i not in done), default=None)
        if nxt is None:
            break
        t = nxt                    # advance to the next completion
        done |= {i for f, i in running if f <= t}

    return max(finish), start, assign


TIMES = [3, 2, 2, 2, 4, 4, 4, 4, 9]
PRECEDENCE = {8: [0], 4: [3], 5: [3], 6: [3], 7: [3]}   # T1->T9 ; T4->T5..T8
PRIORITY = list(range(9))                                # the list L = T1..T9
def report(label, times, preds, m, order=None):
    ms, start, assign = list_schedule(times, preds, m, order or PRIORITY)
    print(f"{label}\n  makespan = {ms:g}")
    for p in range(m):
        row = sorted((start[i], i) for i in range(9) if assign[i] == p)
        line = "  ".join(f"T{i+1}[{s:g},{s+times[i]:g})" for s, i in row)
        print(f"    P{p+1}: {line}")
    print()

Baseline: makespan 12

\(P_1\) T1 [0,3) T9 [3,12)
\(P_2\) T2 [0,2) T4 [2,4) T5 [4,8) T7 [8,12)
\(P_3\) T3 [0,2) idle [2,4) T6 [4,8) T8 [8,12)

\(T_1\) finishes at 3, releasing \(T_9\), which runs 3 → 12. The chain \(T_1 \to T_9\) costs \(3 + 9 = 12\), and that is also the makespan, so this schedule is optimal. One processor idles from 2 to 4 and it costs nothing.

Anomaly 1: every task gets faster → 13

Subtract 1 from every execution time. Every single task now finishes sooner, and the program finishes later.

\(P_1\) T1 [0,2) T5 [2,5) T8 [5,8)
\(P_2\) T2 [0,1) T4 [1,2) T6 [2,5) T9 [5,13)
\(P_3\) T3 [0,1) T7 [2,5)

Follow the mechanism. \(T_4\) now takes 1 unit instead of 2, so it finishes at \(t = 2\) rather than \(t = 4\) — which means \(T_5, T_6, T_7, T_8\) become ready at \(t=2\). At that same instant \(T_1\) has also finished, so \(T_9\) is ready too. Five tasks compete for three processors, and the priority list says \(T_5, T_6, T_7\) come before \(T_9\). The long task is shut out until \(t = 5\), and \(5 + 8 = 13\).

Making the predecessors faster released the competitors earlier. In the baseline, \(T_9\)’s only rivals at \(t = 3\) were tasks that were not ready yet.

Anomaly 2: add a processor → 15

Same times, same graph, \(m = 3 \to 4\).

\(P_1\) T1 [0,3) T8 [3,7)
\(P_2\) T2 [0,2) T5 [2,6) T9 [6,15)
\(P_3\) T3 [0,2) T6 [2,6)
\(P_4\) T4 [0,2) T7 [2,6)

With only three processors, \(T_4\) had to wait for one to free up and did not finish until \(t = 4\). With four, \(T_4\) starts immediately and finishes at \(t = 2\) — so \(T_5 \dots T_8\) are ready at 2 instead of 4. Again they outrank \(T_9\), which cannot start until 6. \(6 + 9 = 15\).

The extra processor was used to unblock work that then crowded out the critical task.

Anomaly 3: remove the dependencies → 16

Same times, same three processors, but now every task is independent. Strictly fewer constraints.

\(P_1\) T1 [0,3) T6 [3,7) T9 [7,16)
\(P_2\) T2 [0,2) T4 [2,4) T7 [4,8)
\(P_3\) T3 [0,2) T5 [2,6) T8 [6,10)

\(T_9\) is now ready at \(t = 0\) — but it is last in the list, so all eight other tasks are started ahead of it. It does not begin until \(t = 7\), and \(7 + 9 = 16\).

This is the purest form of the pathology. The precedence constraints in the baseline were accidentally acting as a scheduling hint: by keeping \(T_5 \dots T_8\) blocked, they left a processor free for \(T_9\) at exactly the right moment. Remove the constraints and you remove the accidental hint.

The pattern, in one sentence

List scheduling is not monotone: making the instance easier — faster tasks, more processors, fewer constraints — can make the schedule worse, because the priority list is fixed while the set of ready tasks changes underneath it.

The scheduler is greedy over the ready set. Anything that enlarges the ready set earlier gives low-priority-but-long tasks more competition, and a long task started late sets the makespan.

A fourth one: change the priority list

The three classic anomalies change the instance. The list itself is just as dangerous, and this is the version you meet in practice — because a real scheduler’s priority order comes from estimates, and estimates drift.

Keep everything at baseline and merely reverse the list to \(L' = (T_9, T_8, \dots, T_1)\):

Fix the priority and most of the pathology goes with it — which is precisely what every list-scheduling heuristic in Section 5 is trying to do, and what “static level” and “upward rank” compute.

Checking Graham’s bound yourself

The bound below is easy to test empirically, and doing so is a good way to convince yourself the anomalies are bounded rather than arbitrary:

import random

def random_dag(n, edge_p, rng):
    times = [rng.randint(1, 9) for _ in range(n)]
    preds = {}
    for i in range(n):                       # only edges j -> i with j < i, so acyclic
        ps = [j for j in range(i) if rng.random() < edge_p]
        if ps:
            preds[i] = ps
    return times, preds


rng = random.Random(7)
worst_ratio, worst_at = 0.0, None
for _ in range(4000):
    n = rng.randint(5, 12)
    times, preds = random_dag(n, 0.25, rng)
    m, m_prime = rng.randint(2, 4), rng.randint(2, 6)
    order = list(range(n))
    t_m,  _, _ = list_schedule(times, preds, m,       order)
    t_mp, _, _ = list_schedule(times, preds, m_prime, order)
    ratio, bound = t_mp / t_m, 1 + (m - 1) / m_prime
    assert ratio <= bound + 1e-9, "Graham's bound violated!"
    if ratio > worst_ratio:
        worst_ratio, worst_at = ratio, (m, m_prime, bound)

m, m_prime, bound = worst_at
print(f"4000 random DAGs, bound never violated.")
print(f"worst observed T_m'/T_m = {worst_ratio:.3f}  "
      f"(m={m} -> m'={m_prime}, bound 1+(m-1)/m' = {bound:.3f})")

worst observed T_m'/T_m = 2.000  (m=4 -> m'=2, bound 1+(m-1)/m' = 2.500)

Note the assertion never fires — but the worst observed ratio is 2.0, i.e. one of those random graphs took twice as long after the processor count changed. The anomalies are not rare pathologies you can ignore; they are ordinary behaviour of a greedy scheduler on a random graph.

The bound on the damage

Graham also proved the anomalies are bounded.23 Going from \(m\) to \(m'\) processors with the same list:

\[\frac{T_{m'}}{T_{m}} \;\leq\; 1 + \frac{m-1}{m'}\]

So the damage is limited — doubling the cluster can never more than roughly halve your gains — but it is emphatically not zero.

What to take away

  • Greedy is within \(2\times\), but not monotone: local improvements are not safe.
  • “It got slower after we upgraded” is a legitimate scheduling outcome.
  • All of this assumed exact, known execution times. That assumption is about to collapse.

5. Static scheduling algorithms

Two axes first

Before the algorithms, two distinctions that the literature assumes you know.

Static vs. dynamic. A static scheduler decides everything before execution starts, from a cost model. A dynamic one decides while running, from what it observes. Sections 5 and 6 of this document are exactly that split.

Preemptive vs. non-preemptive. A preemptive scheduler may interrupt a running task and resume it later (or elsewhere); a non-preemptive one, once started, must let a task run to completion. Everything in this lecture is non-preemptive — which is why a badly-placed long task, as in Section 4, cannot be rescued once it starts.

What “heuristic” means here

A heuristic is what you use when exact methods are too slow, or fail to find any solution at all in the search space. It trades optimality, completeness, accuracy or precision for speed. Every algorithm below is a heuristic in that sense: none of them is guaranteed optimal, and all of them run in something like \(O(v \log v + e)\) rather than exponential time.

The families

Given that optimality is out of reach, the literature is a catalogue of heuristics.24 They fall into a few families.

List scheduling. Assign every node a priority, sort, and repeatedly place the highest-priority ready node on the processor that allows the earliest start. Cheap, and the source of the \(2\times\) bound. Everything above is list scheduling.

The whole family differs only in how the priority is computed, and Section 4 tells you what a good priority must do: get long, critical tasks started early. The standard ones, roughly in order of sophistication:

heuristic priority idea
random / FIFO arbitrary the baseline; what Graham’s anomalies attack
LPT longest processing time for independent tasks only; gives the \(\frac{4}{3} - \frac{1}{3m}\) bound
HLFET static level (longest path to an exit, ignoring communication) “highest level first with estimated times”
MCP as-late-as-possible start time modified critical path; break ties by successors
ETF earliest start time over all ready tasks recomputed each step, so it reacts to the partial schedule
DLS dynamic level = static level minus earliest start balances criticality against availability

The important observation: these differ only in priority, all are \(O(v \log v + e)\) or thereabouts, and all sit inside the same factor-of-2 guarantee. The guarantee does not distinguish them — measurement does.

Static level, the common ingredient

Most of the table is a variation on one quantity. The static level of a node is the longest path from it to any exit node, counting computation only:

\[\text{sl}(n_i) = w(n_i) + \max_{n_j \in \text{succ}(n_i)} \text{sl}(n_j)\]

A node’s static level is how much work is still ahead of it on the worst path. Scheduling high-static-level nodes first is the direct antidote to the “long task, low priority” failure. Add communication costs to the recurrence and you get the upward rank that HEFT uses.

Clustering. Instead of assigning tasks to processors directly, first group tasks that communicate heavily into clusters, then map clusters onto machines. The idea is to zero out the expensive edges by putting their endpoints on the same processor — an edge whose endpoints share a processor costs nothing.

Clustering assumes, initially, an unbounded number of processors, which makes the problem cleaner: decide only what runs together, not where. Then a second phase maps the resulting clusters onto the machines you actually have, and a third orders the tasks within each cluster. DSC (Dominant Sequence Clustering, Yang & Gerasoulis 1994)25 is the best-known algorithm: it repeatedly merges the two endpoints of the edge that currently lies on the critical path, as long as doing so does not lengthen the path.

Clustering shines when the communication-to-computation ratio (CCR) is high. CCR is a program’s average edge weight divided by its average node weight: a high CCR means moving data dominates doing arithmetic. That is precisely the regime a data-analytics cluster lives in, which is why “co-locate the stages that shuffle between them” is such an effective optimisation in practice.

Guided random search. Genetic algorithms, simulated annealing. Expensive, and only worth it when the schedule will be reused many times.

HEFT / CPOP (Topcuoglu, Hariri & Wu, 2002)26 are the well-known list-scheduling algorithms for heterogeneous machines. They need a full cost matrix \(w(n_i, p_k)\) — every task’s runtime on every processor — plus the communication costs \(c(n_i, n_j)\). They then rank tasks by upward rank (the longest path from the task to any exit, including its own cost) and greedily assign each in turn to whichever processor finishes it earliest.

HEFT, worked

The ranking is the interesting half. Upward rank is the static level with communication folded in, using the average cost across processors (since we do not yet know where anything will run):

\[\text{rank}_u(n_i) = \overline{w}(n_i) + \max_{n_j \in \text{succ}(n_i)}\Big( c(n_i,n_j) + \text{rank}_u(n_j) \Big)\]

Take five tasks on two heterogeneous processors:

task on \(P_1\) on \(P_2\) \(\overline{w}\)
A 4 6 5.0
B 5 3 4.0
C 7 5 6.0
D 3 4 3.5
E 6 8 7.0

with edges \(A\to B\) (cost 2), \(A\to C\) (3), \(B\to D\) (1), \(C\to D\) (4), \(D\to E\) (2).

WCOST = {"A": (4, 6), "B": (5, 3), "C": (7, 5), "D": (3, 4), "E": (6, 8)}
SUCC  = {"A": ["B", "C"], "B": ["D"], "C": ["D"], "D": ["E"], "E": []}
CCOST = {("A", "B"): 2, ("A", "C"): 3, ("B", "D"): 1,
         ("C", "D"): 4, ("D", "E"): 2}

wbar = {t: sum(v) / len(v) for t, v in WCOST.items()}
rank = {}

def rank_u(t):
    if t not in rank:
        rank[t] = wbar[t] + max(
            [CCOST[(t, s)] + rank_u(s) for s in SUCC[t]], default=0)
    return rank[t]

for t in WCOST:
    rank_u(t)

for t, r in sorted(rank.items(), key=lambda kv: -kv[1]):
    print(f"  rank_u({t}) = {r:5.1f}")
print("\nHEFT priority order:",
      [t for t, _ in sorted(rank.items(), key=lambda kv: -kv[1])])
  rank_u(A) =  30.5
  rank_u(C) =  22.5

Read the result: \(A\) ranks highest (30.5) because everything is downstream of it; \(C\) outranks \(B\) (22.5 vs 17.5) even though \(B\) is cheaper on its best processor, because \(C\) sits on the more expensive path to \(D\). That is the algorithm noticing the critical path for you.

The second half of HEFT is then plain greedy: take tasks in rank order and assign each to whichever processor gives the earliest finish time, accounting for when its inputs will have arrived. CPOP is the same machinery with a twist — it computes both upward and downward rank and adds them. Downward rank is the mirror image — the longest path from the entry node down to \(n_i\), excluding \(n_i\)’s own cost:

\[\text{rank}_d(n_i) = \max_{n_j \in \text{pred}(n_i)}\Big( \text{rank}_d(n_j) + \overline{w}(n_j) + c(n_j,n_i) \Big)\]

The sum \(\text{rank}_d + \text{rank}_u\) is constant along the critical path and smaller everywhere else, so it identifies that path exactly. CPOP pins every task on it to whichever single processor minimises the path’s total cost, and schedules the rest greedily around them.

Which to use

  • Homogeneous machines, cheap communication — plain list scheduling with static levels. Anything fancier is noise.
  • High communication-to-computation ratio — clustering.
  • Heterogeneous machines, known costs — HEFT or CPOP.
  • Costs unknown or changing — none of the above. That is Section 6.

HEFT is a good algorithm. Keep the cost matrix in mind though — it is exactly what the next section takes away.

6. Dynamic scheduling

This is the other section that reads badly on slides, because it is a chain of arguments rather than a list of facts. The chain is: static scheduling assumes information nobody has → so stop computing schedules and compute policies → here are the policies, and what each one costs.

Why the static picture breaks

HEFT wants \(w(n_i, p_k)\) and \(c(n_i, n_j)\) for every task and processor before anything runs. Ask where those numbers would come from in a real analytics cluster:

  • A task’s duration depends on data it has not read yet. How many rows survive that filter? You find out by running it.
  • The machine is shared — noisy neighbours, thermal throttling, a cold page cache.
  • The first execution includes JIT warm-up and import time, so it is not representative of the second.
  • Workers appear and disappear: autoscaling, spot instance reclamation, OOM kills.
  • \(c(n_i, n_j)\) is zero if the data is already on that worker and seconds if it is not — which is the very thing you are trying to decide.

And the graph itself may not be finished. dask.dataframe does not know partition sizes until it reads them; shuffles produce structure that depends on the data; interactive users append to the graph while earlier parts are still running.

The pivot

Stop computing a schedule. Compute a policy: a cheap rule, re-evaluated constantly, that is good on average and recovers from being wrong.

Everything in the rest of this section is one such policy, plus the price it charges.

Work sharing vs. work stealing

Two ways to balance load:

  • Work sharing — when a processor creates new work, it pushes it out to a central pool or another processor. Migration happens whenever work is created.
  • Work stealing — an idle processor pulls work from a busy one. Migration happens only when a processor runs dry.

Stealing wins for a reason that is easy to state and easy to underrate: when everybody is busy, stealing costs nothing at all. No messages, no contention, no shared state touched. Communication is proportional to the imbalance, not to the amount of work. Work sharing pays a cost on every task creation, which is exactly the common case.

The deque discipline

Each worker owns a double-ended queue of tasks, and the two ends are used differently. This is the detail that makes work stealing fast, and it is worth being precise about.

The owner pushes and pops its own bottom end — LIFO. Last in, first out is a depth-first traversal of the computation. That means the data the worker needs next is the data it just produced, still sitting in L1/L2 cache. Depth-first also keeps the memory footprint small, because you finish subtrees rather than accumulating a frontier of half-done ones.

The thief takes from the top end — FIFO. The oldest entry in the deque sits nearest the root of the computation, so it is usually the largest remaining subtree. One expensive steal therefore buys a long stretch of work the thief can then run locally without stealing again. Stealing small recent tasks would mean stealing constantly.

And because the two ends are different, owner and thief almost never touch the same slot. The common path — owner pushing and popping its own end — needs no lock at all. That is Cilk’s THE protocol27: synchronisation only when the deque is nearly empty and the two ends might actually meet.

So the deque is not an arbitrary data-structure choice. Each end is doing a different job: one optimises locality, the other optimises how much a steal is worth, and their separation is what removes the lock.

Why the lock disappears

It is worth being concrete about the last point, because “needs no lock” sounds like hand-waving. The owner works at the bottom of the deque, thieves at the top. Each keeps an index; the owner’s pop decrements its index and the thief’s steal increments its own, and each then checks whether the two have crossed.

  • If they have not crossed, there were at least two items, the two parties touched different slots, and no synchronisation was needed at all.
  • If they have crossed, the deque is nearly empty and there is a genuine race over the last item — so fall back to a real lock, which happens rarely.

That is Cilk’s THE protocol28 in outline. The point is the shape of the argument, and it recurs everywhere in this section: make the common case synchronisation-free, and pay only in the rare case.

The theory: Blumofe & Leiserson (1999)29

For a fully strict computation — one where a task’s results are used only by its parent, the shape that spawn/sync code produces — with work \(T_1\) and span \(T_\infty\), randomized work stealing on \(P\) processors achieves

\[\mathbb{E}[T_P] \;=\; \frac{T_1}{P} + O(T_\infty)\]

Warning

Notation. This is Cilk’s convention: \(T_1 = W\) (time on one processor \(=\) work) and \(T_\infty = S\) (time on unlimited processors \(=\) span). Note this \(T_1\) is unrelated to task \(T_1\) in Section 4.

Compare that with the greedy bound from Section 2: it is the same shape. Work stealing is provably within a constant factor of optimal — while knowing nothing about task durations, which is precisely what HEFT needed and could not get.

Two further bounds matter more in practice than the headline one:

  • Space: \(S_P \leq P \cdot S_1\). Stealing cannot blow memory up more than linearly in \(P\). (This is the depth-first discipline paying off.)
  • Communication: expected \(O(P \, T_\infty \, S_{\max})\) bytes, where \(S_{\max}\) is the largest stack frame — proportional to the span, not the work.

Why pick victims at random?

A thief picks its victim uniformly at random: no load table, no coordination, no central state.

The justification is a probabilistic one. If a constant fraction of deques are non-empty, a random steal succeeds with constant probability, so \(O(P)\) steal attempts suffice per unit of progress — which is exactly what the bound above needs. And any attempt to be cleverer — “steal from the most loaded worker” — reintroduces the shared, contended state that stealing existed to avoid.

The work-first principle

Cilk’s design rule:30 move overhead off the work path and onto the critical path. The work path executes \(T_1\) times; the steal path executes only \(O(P \, T_\infty)\) times. So make the common case free and let stealing be expensive. Almost every fast work-stealing runtime is an application of this one principle.

Locality vs. load balance

Two goals pull in opposite directions:

  • balance — keep every processor busy \(\Rightarrow\) move tasks freely
  • locality — run a task where its input already is \(\Rightarrow\) never move tasks

Moving a task is cheap. Moving its 200 MB input is not.

Delay scheduling (Zaharia et al., 2010)31 resolves this with almost embarrassing simplicity: when the next task’s preferred node is busy, wait a few seconds instead of launching it elsewhere. Slots free up constantly, so a short wait almost always wins the local slot. In the Hadoop fair scheduler this raised data locality to nearly 100% and roughly doubled throughput — from about five lines of policy.

Sampling instead of state

The power of two choices.32 Place a task on a uniformly random worker out of \(n\), and the maximum queue length is \(\Theta(\log n / \log\log n)\). Sample two at random and take the shorter queue, and it drops to \(\Theta(\log\log n)\) — an exponential improvement for one extra probe.

Why schedulers care: it means you can get near-centralized placement quality with no centralized state at all. Sparrow33 builds an entire distributed scheduler from this, adding batch sampling and late binding — place reservations on several workers and let whichever frees up first actually claim the task.

Stragglers

In a 10 000-task stage the makespan is set by the slowest task, not the average one. Causes are mundane: a failing disk, a hot node, skewed data, a background daemon, a GC pause.

Speculative execution is the standard answer — once a stage is nearly done, launch duplicate copies of the laggards and take whichever finishes first. The refinements are a nice illustration of a policy being tuned over a decade:

  • MapReduce (2004) — back up the last few tasks near the end of a phase34
  • LATE (2008) — rank by longest approximate time to end, not progress so far; crucial on heterogeneous nodes
  • Mantri (2010) — diagnose the cause (data skew vs. slow node) before acting
  • Dolly (2013) — for small jobs, just clone every task up front; cheaper than detecting stragglers

Speculation is not free, and the trade-off is worth stating plainly: you are spending cluster capacity to buy latency. Duplicating the last 5% of a stage costs at most 5% extra work; duplicating aggressively on a busy cluster can cost far more and slow down everyone else’s jobs. Every refinement in the list above is really an attempt to spend that budget more precisely — which is why they progress from “back up the last few” to “diagnose the cause first”.

The tail at scale (Dean & Barroso, 2013)35 explains why this matters so much more at scale than intuition suggests. If one machine answers within 10 ms 99% of the time, a request fanning out to 100 machines waits longer than 10 ms 63% of the time. Rare slowness at the component level is the common case at the system level. Hence hedged requests, tied requests, micro-partitioning, and “good enough” partial answers.

The scheduler is itself a parallel program

Every policy above is work the scheduler does while jobs are running, and you now own its costs:

  • A decision must be cheaper than the task it schedules — this is what sets your minimum useful task size, and it is why the granularity dial from Section 1 matters.
  • The scheduler holds state proportional to the graph, not the cluster. A million tasks means a million objects in one process.
  • Each policy can misfire: stealing can thrash, speculation can double your cluster load, locality delay can idle machines.

What the frameworks actually do

The theory above describes shared-memory work stealing, where a “task” is a function call and a steal is a pointer swap. Distributed analytics frameworks face the same problem with tasks that are milliseconds to seconds long and data that must cross a network, so they mix the ideas rather than adopting one:

  • Cilk, Intel TBB, Java’s ForkJoinPool, Rust’s Rayon are work stealing in the textbook sense — per-worker deques, random victims, LIFO/FIFO ends.
  • Dask uses a central scheduler that holds the whole graph and assigns tasks to workers, with work stealing layered on top for balance. Because the scheduler sees the graph, it can also order tasks to keep memory small — the depth-first preference a deque gives you for free, dask.order has to compute explicitly. (This is the subject of Lecture 5.)
  • Spark is more static: the DAG scheduler splits the job into stages at shuffle boundaries, and a task scheduler places each stage’s tasks using locality preferences, delay scheduling and speculation.

The common thread is that none of them computes a schedule up front. They all maintain a ready set and apply a cheap rule to it — which is exactly the pivot above.

7. Beyond one framework

There are really two scheduling problems, and they are mostly independent.

The first is the one above: given workers, place tasks. The second is cluster resource management — those workers are processes on machines somebody has to hand out, to this job and to fifty other tenants at the same time.

The second problem is harder, not easier, because it adds multi-tenancy, fairness, preemption and failure across jobs that know nothing about each other. Your framework’s scheduler optimises one job; the cluster manager arbitrates between jobs that would each happily take everything.

Four architectures

They differ mainly in who holds the state and who makes the decision. The trade-off is always the same: decision quality against decision latency and contention.

architecture who decides example trade-off
monolithic one scheduler, full cluster state Borg36, early Hadoop best decisions, single bottleneck, hard to evolve
two-level a resource manager offers slices; frameworks accept or decline Mesos37, YARN frameworks stay independent; each sees only what it is offered
shared-state many schedulers, each with an optimistic copy of full state Omega38 parallel decisions resolved by atomic commit; conflicts under contention
distributed many independent schedulers, no shared state, sampling Sparrow39 millisecond decisions at scale; no global view, so no global guarantees

A few more worth knowing by name:

system idea
YARN (2013) two-level, but by request rather than by offer; a per-application master negotiates with a global resource manager
Kubernetes filter (predicates) \(\to\) score (priorities) \(\to\) bind; a pluggable scheduling framework, and the open descendant of Borg and Omega40
Quincy (2009)41 / Firmament (2016)42 encode fairness and locality as a min-cost flow problem and solve it exactly — optimal placement, at the cost of solving a flow problem per scheduling round

Notice this is the same progression as Section 6, one level up: from a central authority with perfect information toward cheap local decisions with statistical guarantees — and for the same reason. At scale, the cost of knowing exceeds the value of knowing.

Dominant resource fairness

What does “half the cluster” mean when one job wants CPU and another wants memory? DRF43 answers it. Each job’s dominant resource is whichever it uses the largest share of; its dominant share is that fraction. DRF then equalises dominant shares across jobs.

The canonical example: a cluster with 9 CPUs and 18 GB of memory, and two users whose tasks demand

  • user A: ⟨1 CPU, 4 GB⟩ per task — 1/9 of the CPU, 2/9 of the memory, so memory is dominant
  • user B: ⟨3 CPU, 1 GB⟩ per task — 1/3 of the CPU, 1/18 of the memory, so CPU is dominant
CPU, MEM = 9, 18
DEMAND = {"A": (1, 4), "B": (3, 1)}

def dominant_share(n, demand):
    return max(n * demand[0] / CPU, n * demand[1] / MEM)

feasible = [
    (a, b)
    for a in range(10) for b in range(10)
    if a * DEMAND["A"][0] + b * DEMAND["B"][0] <= CPU
    and a * DEMAND["A"][1] + b * DEMAND["B"][1] <= MEM
    and abs(dominant_share(a, DEMAND["A"])
            - dominant_share(b, DEMAND["B"])) < 1e-9
]
a, b = max(feasible, key=lambda ab: dominant_share(ab[0], DEMAND["A"]))

print(f"A runs {a} tasks, B runs {b} tasks")
print(f"equal dominant share = {dominant_share(a, DEMAND['A']):.3f}")
print(f"CPU used {a*1 + b*3}/{CPU}, memory used {a*4 + b*1}/{MEM}")
A runs 3 tasks, B runs 2 tasks
equal dominant share = 0.667
CPU used 9/9, memory used 14/18

A gets 3 tasks and B gets 2, each ending with a dominant share of 2/3 — A using 12 of the 18 GB, B using 6 of the 9 CPUs. Between them they saturate the CPU exactly, and neither can be given more without pushing the other’s dominant share below the shared value.

DRF caught on because it does the obvious right thing in the easy cases (with one resource it reduces to ordinary fair sharing) while being strategy-proof: a user cannot get more by lying about their demands. It is the default in Mesos and YARN.

Scale, for perspective

The numbers explain why the cheap policies win:

  • a Borg cell: tens of thousands of machines, one logically centralized scheduler, placing on the order of 10 000 tasks per minute
  • Sparrow: sub-second tasks with millisecond placement decisions, spread over many independent schedulers
  • a Dask scheduler: a few thousand tasks per second, single-threaded Python

Four orders of magnitude apart in task size — which is why they are different problems with different answers, not one problem solved better or worse.

At those rates a scheduler that takes 100 ms to make a good decision is worse than one that takes 1 ms to make a decent one — which is the whole argument for the right-hand end of the architecture table.

8. The honest summary

Scheduling turned out to mean four different things, and the lecture visits them in order:

  1. A graph problem — recover the partial order hiding inside a total order.
  2. A theory — work, span, and a greedy bound that is within \(2\times\) and cannot be much improved.
  3. A collection of heuristics — because optimality is NP-hard, and because the inputs the heuristics want do not exist.
  4. A running system — policies that are cheap, wrong sometimes, and recover.

Where the theory still earns its keep: \(W\) and \(S\) tell you the ceiling before you write any code, and they tell you which of your two knobs to turn. Graham’s anomalies tell you not to trust local improvements. And the Blumofe–Leiserson bound tells you that a scheduler which knows nothing about your task durations can still be within a constant factor of one that knows everything — which is why every modern framework schedules dynamically.
