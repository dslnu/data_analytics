Definition

Data warehousing is a collection of decision support technologies, aimed at enabling the knowledge worker (executive, manager, analyst) to make better and faster decisions.

Even worse definition

A data warehouse is a “subject-oriented, integrated, time- varying, non-volatile collection of data that is used primarily in organizational decision making.”

Warehouses are OLAP Gen 1.

OLTP vs OLAP

Data warehouse

  • It is a separate database that analysts can query without affecting OLTP operations.

  • The data warehouse contains a read-only copy of the data in all the various OLTP systems in the company.

Extract–Transform–Load (ETL)

  1. Data is extracted from OLTP databases (using either a periodic data dump or a continuous stream of updates)
  2. transformed into an analysis-friendly schema
  3. cleaned up
  4. and then loaded into the data warehouse.

OLTP vs OLAP

Why separate?

  • trying to execute complex OLAP queries against the operational databases would result in unacceptable performance.
  • decision support requires non-OLTP data, such as historical data
  • decision support requires consolidating data from many heterogeneous sources
  • supporting the multidimensional data models and operations typical of OLAP requires special data organization, access, and implementation methods

Dimensional model

  • Multidimensional data model: a set of numeric measures that are the objects of analysis.

  • Each of the numeric measures depends on a set of dimensions

  • A measure as a value in the multidimensional space of dimensions.

  • Each dimension is described by a set of attributes.

Star schema

The name “star schema” comes from the fact that when the table relationships are visualized, the fact table is in the middle, surrounded by its dimension tables; the connections to these tables are like the rays of a star.

  • fact table – collection of events occurring at particular time
  • dimension table – who, what, where, when, how, and why of the event.

OLTP vs OLAP

Dimensional modeling

Designing a star schema

Kimball’s four-step process

  1. Choose the business process: which event are we measuring? (sales, taxi trips, clicks, shipments)
  2. Declare the grain: what exactly does one row of the fact table represent?
  3. Identify the dimensions: the who, what, where, when and how of each row
  4. Identify the facts: the numeric measures recorded in each row

Order matters

The grain is fixed before the dimensions and facts. Every dimension and every fact must be true at that grain.

Grain

Examples of grain statements

  • “One row per line item on a cash register receipt”
  • “One row per taxi trip”
  • “One row per account per day”
  • “One row per order, updated as it moves through fulfilment”

Rules of thumb

  • Prefer the atomic grain, i.e. the lowest level the source provides: you can always roll up, but you can never drill down below the stored grain.
  • Never mix grains in one fact table (e.g. daily rows and monthly totals): SUM will double-count.

Fact table types

Transaction Periodic snapshot Accumulating snapshot
One row per event entity per period instance of a process
Example a sale, a trip account balance per day an order: placed → paid → shipped → delivered

Date keys one one (snapshot date) several, one per milestone
Density sparse: no event, no row dense: a row even if nothing happened one row per instance

Which one?

Most warehouses have all three. They answer different questions: “how much did we sell?” (transaction), “what was the stock level on Friday?” (periodic snapshot), “how long does an order take to ship?” (accumulating snapshot).

Additivity of measures

Additive

Can be summed along all dimensions: quantity, revenue, fare, trip distance.

Semi-additive

Can be summed along some dimensions, but not along time: account balance, inventory level, headcount. Summing balances across accounts is fine. Summing them across days is meaningless: use AVG or the last value instead.

Non-additive

Can never be summed: ratios, percentages, unit prices, temperatures.

Non-additive measures

Example

trip fare tip tip %
1 10 5 50%
2 100 10 10%
  • avg(tip_pct) = 30%
  • sum(tip) / sum(fare) = 15 / 110 = 13.6%

Rule

Store the additive components (numerator and denominator) in the fact table. Compute the ratio after aggregation.

Factless fact tables

Definition

A fact table with no measures, only foreign keys. It records that something happened (or could have happened).

  • Events: student attendance, one row per (date, student, course)
  • Coverage: which products were on promotion in which store on which day

Queries

  • Events: COUNT(*) is the measure.
  • Coverage tables answer “what did not happen?”: products on promotion that sold nothing = coverage EXCEPT sales.

Surrogate keys

Definition

Dimension rows are identified by a surrogate key: a meaningless integer generated by the warehouse. The natural key from the source system (customer email, product SKU) is kept as an ordinary attribute.

Why?

  • natural keys from different source systems collide or are formatted differently
  • source systems reuse or change their keys
  • keeping history (SCD type 2, below) needs several rows per customer
  • small integers make the fact table smaller and joins faster
  • special rows such as “Unknown” or “Not applicable” (keys -1, -2) replace NULL foreign keys

Date dimension

Why a table, when SQL has date functions?

  • business calendar attributes cannot be computed from a date: public holidays, fiscal year, sales seasons, school holidays
  • every report uses the same labels (“2025-Q3”, “Wednesday”)
  • it is tiny: 100 years ≈ 36,500 rows

Time of day

Keep it as a separate dimension (1,440 rows for minutes, 86,400 for seconds) rather than one date-time dimension: one row per second for 100 years would be 3 billion rows.

Other dimension patterns

Degenerate dimension

A dimension key with no dimension table: the receipt or order number stored in the fact table. Used to group line items into a receipt.

Junk dimension

Low-cardinality flags and indicators (payment type, is_gift, is_online) combined into one small dimension containing all combinations. Avoids many tiny dimensions or many flag columns in the fact table.

Role-playing dimension

One physical dimension used in several roles: order date and ship date, pickup zone and dropoff zone.

Conformed dimensions

A dimension is conformed when it means the same thing in every fact table that uses it: same keys, same attribute names, same values.

This allows drill-across: combining results from different fact tables, e.g. sales vs. inventory by product and month.

OLAP cubes

OLTP vs OLAP

OLAP cubes

Materialized aggregates: data warehouse queries often involve an aggregate function, such as COUNT, SUM, AVG, MIN, or MAX in SQL.

If the same aggregates are used often, they can be modified to be materialized.

Relational model offers materialized views.

OLTP vs OLAP

OLTP vs OLAP

Operations

  • rollup: increasing the level of aggregation
  • drill-down: decreasing the level of aggregation or increasing detail along one or more dimension hierarchies
  • slice-and-dice: selection and projection
  • pivot: re-orienting the multidimensional view of data

OLTP vs OLAP

Pivoting

The simplest view of pivoting is that it selects two dimensions that are used to aggregate a measure.

Rollup

Rollup corresponds to taking the current data object and doing a further group-by on one of the dimensions.

A converse is called drill-down.

Slice-and-dice

Slice-and-dice corresponds to reducing the dimensionality of the data, i.e., taking a projection of the data on a subset of dimensions for selected values of the other dimensions.

From cube operations to SQL

Operation SQL
slice WHERE on one dimension: WHERE d.year = 2025
dice WHERE on several dimensions: WHERE d.year = 2025 AND s.region = 'West'
rollup a coarser GROUP BY; GROUP BY ROLLUP (...) adds subtotals
drill-down a finer GROUP BY: add the next level of a hierarchy (region → city)
pivot PIVOT, or one sum(...) FILTER (WHERE ...) per output column
many aggregations at once GROUP BY CUBE (...), GROUP BY GROUPING SETS (...)
comparisons, running totals, shares window functions: ... OVER (PARTITION BY ... ORDER BY ...)

Note

These are SQL:1999 / SQL:2003 features: they work in DuckDB, PostgreSQL, Snowflake, BigQuery, Spark SQL, etc. PIVOT syntax differs between systems.

GROUP BY CUBE (a, b) produces all \(2^n\) combinations: (a, b), (a), (b), (). This is the whole OLAP cube in one query.

Why not UNION ALL?

The same result could be written as a UNION ALL of two GROUP BY queries, but that scans and joins the fact table twice. With GROUPING SETS, the engine can compute all groupings in one pass.

Window functions

Aggregation without collapsing rows

agg(...) OVER (PARTITION BY ... ORDER BY ...) computes an aggregate over a “window” of related rows but keeps every row. Typical OLAP uses:

  • running totals: year-to-date revenue
  • period-over-period: lag(x, k) is the value \(k\) rows earlier
  • share of total: x / sum(x) OVER (PARTITION BY ...)
  • rankings: rank(), row_number()
con.sql("""
WITH monthly AS (
  SELECT d.year, d.month, sum(f.amount) AS revenue
  FROM fact_sales f JOIN dim_date d USING (date_key)
  GROUP BY d.year, d.month
)
SELECT year, month, revenue,
       sum(revenue) OVER (PARTITION BY year ORDER BY month) AS ytd,
       lag(revenue, 12) OVER (ORDER BY year, month)         AS last_year,
       round(100 * (revenue / last_year - 1), 1)            AS yoy_pct
FROM monthly
ORDER BY year, month
""").df().tail(8)

Window functions run after GROUP BY. That is why they can use the aggregate revenue: here, sum(revenue) OVER (...) is a sum of sums.

DuckDB shortcut

Reusing a column alias (revenue, last_year) later in the same SELECT is a DuckDB extension. In PostgreSQL, repeat the expression or use a CTE.

Data lakes and lakehouses

Data lakes and lakehouses

Data warehouse challenges

  • couple compute and storage into an on-premises appliance. This forced enterprises to provision and pay for the peak of user load and data under management, which became very costly as datasets grew.
  • more and more datasets were completely unstructured, e.g., video, audio, and text documents, which data warehouses could not store and query at all.
  • schema-on-write

Data lakes and lakehouses

Solution

Data lakes aka OLAP Gen 2. Features:

  • schema-on-read
  • low-cost storage systems with a file API that hold data in generic and usually open file formats, such as Apache Parquet.
  • data quality and governance: not solved
  • hence downstream data warehouse (Teradata, AWS Redshift, Snowflake)
  • 2-tier architecture
  • started with HDFS (Apache Hadoop)

Data lakes and lakehouses

Cloud data lake: storage layer

  • Amazon S3
  • ADLS (Microsoft)
  • GCS (Google)

Data lakes and lakehouses

Data lakes and lakehouses

Data lake issues

  • reliability: keeping the data lake and warehouse consistent is difficult and costly. There are subtle differences between the data lake and warehouse engines.

  • data staleness: the data in the warehouse is stale compared to that of the data lake. According to a survey by Dimensional Research and Fivetran, 86% of analysts use out-of-date data and 62% report waiting on engineering resources numerous times per month.

  • limited support for advanced analytics: none of the leading ma- chine learning systems, such as TensorFlow, PyTorch and XGBoost, work well on top of warehouses.

  • total cost of ownership: users pay double the storage cost for data copied to a warehouse

Data lakes and lakehouses

Lakehouses

Compared to data warehouses:

  • based on open direct-access data formats, such as Apache Parquet
  • first-class support for machine learning and data science
  • offer state-of-the-art performance.

Data lakes and lakehouses

Data lakes and lakehouses

Technologies enabling Lakehouse transition

  • Reliable data management on data lakes: Delta Lake, Apache Iceberg
  • Support for machine learning and data science: Spark SQL
  • SQL performance: Databricks Delta Engine, Presto, Trino

Data lakes and lakehouses

Lakehouse definition

Lakehouse is a data management system based on low-cost and directly-accessible storage that also provides traditional analytical DBMS management and performance features such as:

  • ACID transactions
  • data versioning
  • auditing
  • indexing
  • caching
  • query optimization

Data lakes and lakehouses

Lakehouse features

  • transactional metadata layer on top of the object store that defines which objects are part of a table version.
  • SQL performances fixes: caching, auxiliary data structures such as indexes and statistics, and data layout optimizations
  • declarative DataFrame APIs: TensorFlow and Spark MLlib

Data lakes and lakehouses

Lakehouses: Metadata

For instance, Apache Iceberg stores the information about which objects are part of a table in the data lake itself as a transaction log in Parquet format, enabling it to scale to billions of objects per table.

Lakehouses: SQL

  • give up data independence
  • cache in SSD or RAM
  • auxiliary data: statistics, Bloom filter for index, etc.
  • data layout: order records by dimensions, or using space-filling curves (Z-order) and Hilbert curves
  • whitebox compression

Whitebox compression

Columnar storage

Columnar storage

Problems

  • fact tables are wide: 100+, sometimes hundreds of columns
  • typical OLAP queries access only 3-5 columns at a time
  • but scan through millions of rows

Solution

Columnar storage to the rescue!

In OLTP databases, all values from a single row are stored together.

In columnar storage, all the values from a single column are stored together, instead.

Columnar storage

Columnar storage

Vectorization

  • efficient usage of CPU-memory bandwidth
  • compress data so that it fits in CPU L1 cache
  • SIMD

Columnar storage

Sorting

  • help with compression
  • multiple sort orders
  • slow down writes: solution is to use LSM trees

Columnar storage

Bitmap encoding

Lightweight encodings

Idea

Values in one column have the same type and are often similar, so they compress much better than whole rows. Columnar engines use lightweight encodings:

  • fast to decode, much faster than general-purpose compression such as gzip or zstd
  • some operations run directly on encoded data, without decoding
  • chosen per column and per block, based on the data actually in it

Encodings

  • dictionary
  • run-length (RLE)
  • bit-packing
  • frame of reference (FOR)
  • delta

There are also specialised encodings for floats (ALP) and strings (FSST).

Bitmap vs lightweight encodings

Lightweight encodings Bitmap encoding
Layout one value or code per row (or per run) one bit vector per distinct value
Size (\(n\) rows, \(k\) distinct values) dictionary: \(n \cdot \log_2 k\) bits \(n \cdot k\) bits uncompressed; needs RLE or Roaring compression unless \(k\) is small
Main goal small storage, fast scanning and decoding fast evaluation of filters
Filters compare codes or values bitwise operations: a IN (x, y) AND b = z → (Bx OR By) AND Bz; counting is a popcount
Where you see it storage format of Parquet, DuckDB, ClickHouse indexes: Oracle bitmap indexes, Druid and Pinot (Roaring bitmaps), Lucene; PostgreSQL bitmap heap scans

Note

Bitmap encoding is a dictionary encoding laid out as one-hot vectors: more space, but very cheap to combine filters. Modern columnar formats store data with lightweight encodings; bitmaps appear as secondary indexes and at run time (null masks, selection vectors).

Dictionary encoding

Example

Column payment: card, cash, card, card, app, cash

  • dictionary: 0 → app, 1 → card, 2 → cash
  • codes: 1, 2, 1, 1, 0, 2: 2 bits each instead of 4-byte strings

Properties

  • works well for low-cardinality columns: country, status, category
  • WHERE payment = 'card' looks up 'card' in the dictionary once, then compares small integers
  • GROUP BY payment can group by the codes
  • breaks down when almost every value is distinct: the dictionary becomes as big as the column

Run-length encoding (RLE)

Example

Column city: Lviv, Lviv, Lviv, Lviv, Kyiv, Kyiv, Kyiv, Odesa, Odesa

RLE: (Lviv, 4), (Kyiv, 3), (Odesa, 2)

Properties

  • works well when the column has long runs of equal values, i.e. it is sorted or clustered
  • count(*) ... GROUP BY city can be answered from the run lengths alone
  • often combined with dictionary encoding: RLE over dictionary codes
  • on unsorted data it makes things worse: every run has length 1

Bit-packing, frame of reference, delta

Bit-packing

Store each integer using only the bits it needs. Values 3, 0, 6, 5 fit in 3 bits each, not 32.

Frame of reference (FOR)

Subtract the block’s minimum, then bit-pack:

1003, 1017, 1009, 1031 → min 1003 + offsets 0, 14, 6, 28 → 5 bits each instead of 32

Delta

Store the differences between consecutive values:

1700000000, 1700000010, 1700000020, 1700000031 → 1700000000, +10, +10, +11

Ideal for increasing columns: IDs, timestamps. The deltas are then bit-packed.

Which encoding?

Data Preferred encoding
the same value everywhere constant: store one value
long runs of equal values (sorted) RLE
few distinct values dictionary (+ RLE / bit-packing of the codes)
integers in a narrow range frame of reference + bit-packing
increasing integers, timestamps delta + bit-packing
floating-point numbers with few decimal digits ALP
strings with repeating fragments (URLs, e-mails) FSST

Note

Parquet does the same: it encodes each column chunk (dictionary, RLE, delta, …), and can then apply general-purpose compression (Snappy, zstd) on top.

DuckDB’s compression methods

Method Columns in the demo How it works
Constant one; vendor_id in the last row group the whole segment holds one value: store it once
RLE vendor_id (value, run length) pairs
BitPacking trip_id, pickup_ts, zone_id picks a mode per group of values: constant, constant delta (arithmetic sequences: only the start and the step are stored), delta + FOR, or FOR; the result is bit-packed
DICT_FSST payment, url dictionary of the distinct strings, codes bit-packed; the dictionary strings themselves are compressed with FSST
ALP fare floating-point numbers that are really decimals
ALPRD raw_fare “real” doubles with many significant digits
Uncompressed fallback when nothing helps

How DuckDB chooses

When a row group is written (at CHECKPOINT), DuckDB runs an analyze phase for every column: each applicable method estimates the compressed size on the actual data, and the smallest wins. So the same column can use different methods in different row groups, as vendor_id does.

Reading the demo

  • trip_id = 0, 1, 2, … and pickup_ts = every 10 s are arithmetic sequences: constant delta, almost zero bits per value
  • zone_id = 1000–1050: FOR leaves offsets 0–50, i.e. 6 bits instead of 32

ALP: Adaptive Lossless floating-Point compression

Problem

A DOUBLE takes 64 bits. Its bits look random to general-purpose compressors, and older float-specific schemes (Gorilla 2015, Chimp 2022, which XOR each value with the previous one) give modest gains.

Observation

Many doubles are really decimals with few digits: prices, measurements, percentages. 37.45 has no exact binary representation, but 37.45 × 100 rounds to the integer 3745, and 3745 / 100 gives back exactly the same double.

Algorithm (per vector of 1,024 values)

  1. choose a power of ten \(10^e\) by sampling the vector (hence “adaptive”)
  2. encode each value as an integer \(n = \text{round}(v \cdot 10^e)\)
  3. check that decoding \(n / 10^e\) gives back exactly \(v\), bit for bit (hence “lossless”); values that fail are stored separately as exceptions
  4. compress the integers with FOR + bit-packing

fare ranges over 0.00–100.00, i.e. integers 0–10,000: 14 bits instead of 64.

Afroozeh, Kuffó, Boncz, “ALP: Adaptive Lossless floating-Point Compression”, SIGMOD 2024.

ALPRD: “real doubles”

When ALP does not apply

Values like random() * 100 = 37.4518230981... use all ~16 significant digits: no small power of ten turns them into integers.

Idea

Split each 64-bit value into two parts:

  • left part: sign, exponent and the top mantissa bits. Within a column these take few distinct values (the numbers have similar magnitudes), so they are dictionary-encoded with a handful of bits.
  • right part: the remaining mantissa bits, which really are random: stored bit-packed as they are.

Result

Much smaller savings than ALP, but still lossless and fast to decode. Measured on 10 million values in DuckDB, including file overhead: random() * 100 with ALPRD takes ~56 bits per value; round(random() * 100, 2) with ALP takes ~17.

FSST: Fast Static Symbol Table

Idea

  • learn a symbol table from a sample of the strings: up to 255 symbols, each 1–8 bytes long, chosen for frequent substrings
  • each string becomes a sequence of 1-byte codes; code 255 is an escape, followed by a literal byte

Example

Symbols: https://, example., com/, trips/, …

https://example.com/trips/42 (28 bytes) → [https://] [example.] [com/] [trips/] [4] [2] = 6 bytes

Why not LZ4 or zstd?

They compress a whole block, so reading one string means decompressing the block. FSST compresses each string separately: any single string can be decoded on its own (random access), and decoding runs at gigabytes per second. Compression ratios are similar to LZ4.

Boncz, Neumann, Leis, “FSST: Fast Random Access String Compression”, VLDB 2020.

Zone maps

Min/max indexes

For each block of rows, store the minimum and maximum of every column:

  • DuckDB: row groups of 122,880 rows
  • Parquet: row groups, plus page indexes
  • Snowflake: micro-partitions; Iceberg and Delta: per-file statistics

Data skipping

WHERE trip_id BETWEEN 500000 AND 500100 only reads the blocks whose [min, max] range overlaps the condition. The rest are skipped without being read.

Only works on clustered data

If the column is sorted or clustered, block ranges are narrow and disjoint, so most blocks are skipped. If the values are random, every block spans the whole range and nothing can be skipped. This is another reason to sort, or to use Z-order/Hilbert curves when filtering on several columns.

Query execution models

Query execution models

The question

A query plan is a tree of operators (scan → filter → aggregate). How do the operators pass data to each other?

Three answers

  1. Volcano / iterator model: one tuple at a time (PostgreSQL, MySQL, SQLite)
  2. Vectorized execution: one batch of values at a time (DuckDB, ClickHouse, Snowflake, Velox, Polars)
  3. Query compilation: generate machine code for each query (HyPer, Umbra, Spark’s whole-stage codegen)

Volcano (iterator) model

How it works

Every operator implements next(), which returns one tuple. The root pulls tuples through the tree:

Aggregate.next() → Filter.next() → Scan.next()

Pros and cons

  • simple and composable: any operator can be plugged into any other
  • but: several function calls per tuple per operator, often virtual calls or bytecode dispatch
  • the CPU spends more time on this overhead than on the actual work (comparing, adding)
  • no SIMD, poor use of CPU caches
  • fine when disk I/O was the bottleneck, too slow for in-memory analytics

Vectorized execution

How it works

next() returns a vector: a batch of ~1,000–2,000 values per column (2,048 in DuckDB). Each operator runs a tight loop over plain arrays.

# tuple at a time: interpretation overhead for every row
for row in table:
    if row.fare > 50:
        total += row.tip

# vectorized: overhead once per batch, then simple loops over arrays
for batch in table.batches(2048):
    mask = batch.fare > 50          # one loop, compiled to SIMD instructions
    total += batch.tip[mask].sum()  # another loop

Why it is fast

  • the per-call overhead is paid once per batch, not once per row
  • a batch fits in the L1/L2 cache
  • simple loops over arrays let the compiler use SIMD: 4–16 values per instruction
  • it works naturally with columnar storage: a batch is a slice of a column
  • origin: MonetDB/X100 (2005) → Vectorwise → DuckDB, ClickHouse, …

Query compilation

How it works

Generate code (e.g. via LLVM) for each query. Operators are fused into one loop, so values stay in CPU registers between operators:

for (i = 0; i < n; i++)
    if (fare[i] > 50) total += tip[i];

Trade-offs

  • the fastest for long, compute-heavy queries
  • compilation takes time (milliseconds to seconds), which hurts short queries
  • harder to build, debug and profile
  • in practice, systems mix approaches: Spark generates code, PostgreSQL JIT-compiles expressions, and vectorized engines use precompiled loops

Late materialization

Query

SELECT pickup_ts, tip FROM trips WHERE fare > 90 AND zone_id = 1007

Early materialization

Read all four columns, assemble full rows, then filter. Most of the assembled rows are thrown away.

Late materialization

  1. scan fare only → positions of the rows with fare > 90
  2. scan zone_id only at those positions → fewer positions
  3. fetch pickup_ts and tip only for the remaining positions
  4. build result rows at the very end

Columns that are not needed for a row are never read or decoded for it.

Query optimization

From SQL to execution

Pipeline

  1. Parse: SQL text → syntax tree
  2. Bind: resolve table and column names, check types
  3. Logical plan: a tree of relational algebra operators: scan, filter (selection), projection, join, aggregate
  4. Optimize: rewrite the logical plan, choose a join order
  5. Physical plan: choose an algorithm for every operator: hash join or merge join, hash or sort aggregation, …
  6. Execute: Volcano, vectorized or compiled, as above

Why it matters

SQL is declarative: it says what to compute, not how. For the same query, a good plan and a bad plan can differ by orders of magnitude. In analytics, queries scan billions of rows, so the optimizer matters more than anywhere else.

Logical vs physical plan

Logical plan Physical plan
Describes what is computed how it is computed
Operators selection, projection, join, aggregation sequential scan, index scan, hash join, merge join, hash aggregate, sort, …
Chosen by rewrite rules cost-based choices
Example \(\gamma_{city}(\sigma_{year=2025}(sales \bowtie date \bowtie store))\) hash join of fact_sales with a filtered dim_date scan, …

Two kinds of optimization

  • Rule-based: rewrites that (almost) always help, applied without estimating anything
  • Cost-based: choices that depend on the data: join order, join algorithm, build side. Needs cost estimates.

Rule-based rewrites

Common rules

  • Predicate (filter) pushdown: move filters as close to the scans as possible, ideally into the scan itself
  • Projection pushdown: read only the columns that are used later
  • Constant folding and expression simplification: trip_id + 1 = 500001 → trip_id = 500000
  • Subquery unnesting (decorrelation): turn a correlated subquery, which runs once per row, into a join
  • Join elimination: drop a join whose columns are never used and which cannot change the number of rows
  • Filter inference: a.k = b.k AND a.k = 5 implies b.k = 5

Pushdown into storage

Projection pushdown

In a columnar format (DuckDB, Parquet), columns that are not used are never read. A SELECT * on a 100-column table reads 100 columns; selecting 3 reads 3.

Filter pushdown

A filter pushed into the scan can use the zone maps: row groups whose [min, max] cannot match are skipped. Over Parquet files on S3, these blocks are not even downloaded.

Limits

Pushdown only works if the engine can translate the predicate into a range on the stored column. Wrapping the column in an arbitrary function usually prevents this.

Join algorithms

Nested loop join Hash join Sort-merge join
Idea compare every row of \(R\) with every row of \(S\) build a hash table on one input, probe it with the other sort both inputs on the key, then merge them
Cost \(O(|R| \cdot |S|)\) \(O(|R| + |S|)\) \(O(|R| \log |R| + |S| \log |S|)\), or \(O(|R| + |S|)\) if already sorted
Join conditions any, including <, LIKE equality only equality and ranges
Typical use tiny inputs; non-equality conditions the default in analytics inputs already sorted; very large inputs; range joins

Index nested loop join

In OLTP, the inner side is often an index lookup instead of a scan: fast when the outer side has a few rows. Analytical queries usually touch too many rows for that.

Hash join

Two phases

  1. Build: read the smaller input and insert its rows into a hash table on the join key
  2. Probe: stream the larger input; for every row, look up its key in the hash table

Build side matters

The hash table should hold the smaller input. In a star schema the (filtered) dimension tables are the build sides and the fact table is streamed through all the hash tables. In DuckDB’s plans, the build side is the right child of a Hash Join.

When the build side does not fit in memory

Grace hash join: partition both inputs by hash of the key and write the partitions to disk; then join partition \(i\) of \(R\) with partition \(i\) of \(S\), one pair at a time.

Join order

Why it matters

Joins are associative and commutative, so \(n\) tables can be joined in many orders. All orders give the same result, but the intermediate results can differ hugely in size.

Number of left-deep join orders: \(n!\). With 5 tables, 120; with 10 tables, 3.6 million. Bushy trees give even more.

Example

fact_sales (30,700 rows) ⋈ dim_date (filtered to 31 rows) ⋈ dim_store (filtered to 2 rows):

  • join the fact table with the most selective dimension first: the intermediate result shrinks immediately
  • an order that produces a large intermediate result first (e.g. fact ⋈ an unfiltered dimension) does more work at every following step

Cost-based optimization

Ingredients

  1. Statistics about the data: row counts, number of distinct values (often via HyperLogLog), min/max, histograms, null counts
  2. Cardinality estimation: how many rows will each intermediate result have?
  3. Cost model: estimated cost (I/O, CPU, memory) of each physical operator, given its input sizes
  4. Search: enumerate plans and keep the cheapest

Search strategies

  • Dynamic programming over subsets of tables: System R (Selinger et al., 1979), still the classic approach. DuckDB uses DPhyp (Moerkotte & Neumann, 2008)
  • Greedy or randomized heuristics when there are too many tables for dynamic programming

Cardinality estimation

The weak spot of every optimizer

Estimates rely on simplifying assumptions:

  • Uniformity: values are evenly distributed
  • Independence: the selectivity of a AND b is sel(a) × sel(b)
  • Inclusion: every key on one side of a join finds a partner on the other side

Errors compound

Real data has correlations (city = 'Lviv' implies region = 'West') and skew. An error of 10× per join becomes 1000× after three joins. Leis et al., “How Good Are Query Optimizers, Really?” (VLDB 2015): cardinality errors, not the cost model, cause most bad plans.

Demo: estimates vs reality

month and quarter in dim_date are perfectly correlated. Compare DuckDB’s estimates with the actual counts:

con.sql("PRAGMA explain_output = 'physical_only'")
for w in ["month = 12", "quarter = 4", "month = 12 AND quarter = 4", "month = 12 AND quarter = 1"]:
    plan = con.sql(f"EXPLAIN SELECT * FROM dim_date WHERE {w}").fetchall()[0][1]
    estimate = [line for line in plan.splitlines() if "rows" in line][-1].strip("│ ")
    actual = con.sql(f"SELECT count(*) FROM dim_date WHERE {w}").fetchall()[0][0]
    print(f"{w:<30} estimate: {estimate:<10} actual: {actual}")
month = 12                     estimate: ~57 rows   actual: 62
quarter = 4                    estimate: ~183 rows  actual: 184
month = 12 AND quarter = 4     estimate: ~57 rows   actual: 62
month = 12 AND quarter = 1     estimate: ~57 rows   actual: 0
  • month = 12 AND quarter = 1 cannot match any row, yet the estimate is the same as for month = 12.
  • Under the independence assumption, the estimate would be \(731 \cdot \frac{1}{12} \cdot \frac{1}{4} \approx 15\) for both: still wrong.
  • Statistics are per column, so neither approach knows that the columns are correlated. Some systems support multi-column statistics (CREATE STATISTICS in PostgreSQL).

Star joins: runtime filters

Problem

Filters are on the dimensions (year = 2025, region = 'West'), but the expensive part is scanning the fact table, which has no filter of its own.

Solution: sideways information passing

  1. build the hash tables of the filtered dimensions first
  2. derive a filter on the fact table’s foreign keys: the set of keys, their min/max, or a Bloom filter
  3. push it into the fact table scan: rows, and even whole row groups or partitions, are skipped before the join

Also known as semi-join reduction, runtime filters, or dynamic partition pruning (Spark).

Aggregation

Algorithms

  • Hash aggregation: a hash table from group key to running aggregates. The default; one pass over the data.
  • Sort aggregation: sort by group key, then aggregate consecutive rows. Useful when the input is already sorted or there are too many groups for memory.

Optimizations

  • Partial (two-phase) aggregation: each thread or node aggregates its own data first; only the partial results are combined. Essential in parallel and distributed engines: a count(*) over a billion rows sends one number per node, not a billion rows.
  • Aggregation pushdown: aggregate the fact table before joining it to a dimension, so the join processes groups instead of rows.
  • Top-N: ORDER BY ... LIMIT k keeps a heap of \(k\) rows instead of sorting everything.
  • Approximate aggregates: approx_count_distinct (HyperLogLog), approx_quantile: much less memory than the exact versions.

Adaptive query execution

Idea

Estimates are often wrong, so re-optimize during execution, once real sizes are known.

Examples

  • Spark AQE: after each shuffle stage, uses actual partition sizes to switch a sort-merge join to a broadcast hash join, merge small partitions and split skewed ones
  • Runtime filters (above): built from actual data, not estimates
  • some engines choose the hash table size or the join algorithm at run time

Practical checklist

Writing queries that optimize well

  • select only the columns you need; avoid SELECT * on wide tables
  • write filters directly on stored columns: ts >= '2025-03-01' AND ts < '2025-03-02', not strftime(ts, ...) = '...'
  • filter on columns that the data is sorted or partitioned by, so zone maps and partition pruning can work
  • join on keys with the same type, so no conversion is needed on every row
  • prefer GROUPING SETS, window functions and QUALIFY over self-joins and UNION ALL of similar queries

When a query is slow

  • run EXPLAIN ANALYZE and compare estimated with actual row counts: large differences point to a bad plan
  • look for large intermediate results, missing filter pushdown, and full scans where you expected skipping
  • keep statistics up to date: ANALYZE in PostgreSQL (DuckDB keeps them automatically)
